# Faster person segmentation / matting inference in Page2Cam (ONNX Runtime, Rust `ort`)

Scope: RVM MobileNetV3 fp32 (640x360, downsample_ratio 0.4, recurrent r1..r4 round-tripped through CPU `Vec<f32>` every frame; ~31 ms/frame on a Ryzen 5 8600G CPU) and MediaPipe selfie landscape (256x144, ~1 ms). `ort` 2.0.0-rc.15 (`load-dynamic`, features `api-24` and `directml` on Windows), ORT 1.24.4, DirectML 1.15.4. Code reviewed: `crates/p2c-segment/src/{engine.rs,runtime.rs}`. Today is 2026-11-18. Two notes on sources: ort.pyke.io returned HTTP 403 to my fetcher, so `ort` API facts come from the crate source in the local cargo registry (`~/.cargo/registry/src/index.crates.io-*/ort-2.0.0-rc.15/src/`), which is a primary source. I could not reach the docs.rs pages for rc.15 either.

## 1. Session options that matter (optimization level, threads, execution mode, memory pattern, static shapes, saved optimized model)

### Takeaway
The current code takes every default: `Session::builder(env)?.commit_from_file(...)`. All graph optimizations are already on by default, so the cheap wins are elsewhere: fixed shapes (`with_dimension_override`, or a re-exported static model), an explicit thread count with spinning off (Page2Cam shares the CPU with CEF, ffmpeg and webcam decode), and a saved pre-optimized model to cut startup time. On DirectML, memory pattern must be off and execution must be sequential. ort rc.15 also sets an EP selection policy (MaxEfficiency) by default, which is worth knowing about.

### Cited Findings
- **Optimization levels:** Basic rewrites run before partitioning and apply to all EPs. Extended fusions "are only applied to the nodes assigned to the CPU or CUDA or ROCm execution provider". Layout optimizations "are only applied to nodes assigned to CPU execution provider". "All optimizations are enabled by default." — [ORT graph optimizations](https://onnxruntime.ai/docs/performance/model-optimizations/graph-optimizations.html)
- **Saving the optimized model:** set `optimized_model_filepath`; the saved model can then load with optimizations disabled to cut startup time. Caveat: use "the exact same options (e.g., execution providers, optimization level) and hardware as the target machine". A layout-optimized model saved on an AVX2 machine needs "CPUs that support AVX2". — [ORT graph optimizations](https://onnxruntime.ai/docs/performance/model-optimizations/graph-optimizations.html)
- **Threading defaults:** with `intra_op_num_threads=0` the pool gets one thread per physical core plus some affinitization. Setting the count explicitly disables affinity. Sequential execution is the default. The inter-op pool only exists in parallel mode, and parallel mode "could also hurt performance on some models without many branches". — [ORT threading](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)
- **Spinning:** on by default. It "Provides faster inference but consumes more CPU cycles, resources, and power". Keys are `session.intra_op.allow_spinning` and `session.intra_op.spin_duration_us` (0 disables spinning). — [ORT threading](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)
- **`ort` rc.15 builder methods** (crate source, `session/builder/impl_options.rs` and `impl_config_keys.rs`): `with_intra_threads`, `with_parallel_execution(bool)`, `with_optimization_level`, `with_optimized_model_path`, `with_memory_pattern(bool)`, `with_dimension_override(name, size)`, `with_dimension_override_by_denotation`, `with_independent_thread_pool`, `with_intra_op_spinning(bool)`, and `with_auto_device(AutoDevicePolicy)` (feature `api-22`). — ort 2.0.0-rc.15 source (local cargo registry; [repo](https://github.com/pykeio/ort))
- **Default EP policy in ort rc.15:** with `api-22` enabled (Page2Cam enables `api-24`, which implies it), `SessionBuilder::new` calls `SessionOptionsSetEpSelectionPolicy(..., AutoDevicePolicy::MaxEfficiency)`. The comment says "target on-device usage; prefer efficiency by default". The doc comment on `MaxEfficiency` says it is "Currently the same as PreferNPU". — ort rc.15 `session/builder/mod.rs` and `impl_options.rs` ([repo](https://github.com/pykeio/ort))
- **The DirectML EP prefers known shapes:** "The DirectML EP performs best when the sizes of inputs & outputs are known when the session is created. For graphs with dynamically sized inputs, you can override individual dimensions by constructing the session with `SessionBuilder::with_dimension_override`." — ort rc.15 `ep/directml.rs` doc comment; same advice in [ORT DirectML EP docs](https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html)

### Inferences
- **CPU thread budget:** the 8600G has 6 cores / 12 threads, and ORT's default takes all 6 physical cores with spinning on, while CEF rendering, x264 in ffmpeg and MJPEG decode run alongside. Try `with_intra_threads(3..4)` plus `with_intra_op_spinning(false)` (or `spin_duration_us=0`). This may not lower RVM latency in isolation, but it should cut CPU contention and jitter for the rest of the pipeline. Measure both ways in the real app, not only in a microbenchmark.
- **Each session gets its own spinning pool by default.** If both engines can be open at once, a shared environment-level thread pool (ort's `with_global_thread_pool` / `no_global_thread_pool` options; I saw the fields but did not check the exact API) avoids two pools fighting over cores.
- **The default MaxEfficiency policy:** on Linux and on the plain DirectML NuGet build no NPU plugin EP is registered, so it most likely falls back to CPU harmlessly. Still, the policy is set silently. Log `session` device/EP assignment at startup so Windows test reports explain themselves (see Gaps).
- **RVM's dynamic shapes:** RVM's recurrent inputs have dynamic spatial dims, and `downsample_ratio` is a runtime tensor that drives internal Resize sizes. That makes the graph shape-dynamic even at a fixed 640x360 `src`. Fixing `src` with `with_dimension_override` only helps if the model's free dims are named, and the Resize scales stay data-dependent. **Re-exporting RVM with a fixed resolution and a constant downsample_ratio**, using the exporter in RVM's `onnx` branch, is the robust route to fully static shapes. This is my inference from the model design and the DirectML guidance; I found no benchmark.

### Gaps
- No published numbers for RVM's CPU latency versus intra-op thread count. This needs a local sweep (1, 2, 3, 4, 6 threads; spinning on/off) on the 8600G.
- I could not confirm from ORT docs whether an explicitly appended EP (`with_execution_providers([DirectML])`) overrides the EP selection policy set by `ort`'s builder default. Verify on Windows by logging the providers actually used. ORT's verbose log or profiling shows node placement.
- I did not verify that RVM's ONNX input dims carry names that `with_dimension_override` can target. Inspect the model with `onnx`/Netron.
- The memory arena (`enable_cpu_mem_arena`, arena extend strategy) was not researched. For fixed-shape per-frame inference it mostly affects memory footprint, not latency (inference, unverified).
- ORT 1.24.4's actual behaviour when memory pattern or parallel execution is left on with DML (error versus warn and auto-disable) was not verified; the source fetch failed.

## 2. IoBinding: keeping RVM recurrent state on the device; cost of copies

### Takeaway
On CPU, the recurrent-state round trip is just a few memcpys and almost certainly not the bottleneck. Removing the extra `to_vec()` / `clone()` (feeding the output `Value`s straight back as inputs) is a free micro-win. On DirectML, IoBinding with outputs bound to DML device memory and r*o fed back as r*i is exactly what RVM's authors recommend, and `ort` rc.15 has every API needed (`create_binding`, `bind_input`, `bind_output`, `bind_output_to_device`, `run_binding`, `AllocationDevice::DIRECTML`, `Tensor::to(device, id)`). Only `pha` (640x360 f32, about 0.9 MB) needs to come back to the CPU.

### Cited Findings
- **RVM's own guidance:** the naive loop moves recurrent states between CPU and GPU every frame when they "could have just stayed on the GPU for better performance". Its IO-binding example keeps the states as device tensors and copies only `fgr`/`pha` back. The example is Python with the CUDA EP, and the page warns ORT "may not support all the operations in our official ONNX model". — [RVM inference docs](https://github.com/PeterL1n/RobustVideoMatting/blob/master/documentation/inference.md)
- **When IoBinding helps:** the `ort` doc comment says it suits outputs that "should stay on a device", ensembles, and constant inputs. It gives no meaningful benefit for "Pipelines that go straight from CPU -> GPU -> CPU" or models where every input changes. — ort rc.15 `session/io_binding.rs` ([repo](https://github.com/pykeio/ort))
- **API surface in ort rc.15:** `Session::create_binding()`; `IoBinding::bind_input(name, &Value)`; `bind_output(name, Value)`; `bind_output_to_device(name, &MemoryInfo)`; `synchronize()`; `Session::run_binding(&IoBinding)`. Memory: `AllocationDevice::DIRECTML` (`c"DML"`), `Allocator::new(&session, MemoryInfo::new(device, id, AllocatorType::Device, MemoryType::Default))`, `Tensor::to(device, device_id)`, `copy_into`, `copy_into_async`. There is also a DirectML-specific helper to wrap a D3D12 resource as a tensor. — ort rc.15 `session/io_binding.rs`, `memory.rs`, `value/impl_tensor/copy.rs`, `ep/directml.rs` (local source; [docs.rs rc.10 IoBinding](https://docs.rs/ort/2.0.0-rc.10/ort/io_binding/struct.IoBinding.html) for the matching signatures)
- **Threading on DirectML:** only one thread may call `Run` on a session at a time. — [ORT DirectML EP](https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html)

### Inferences
- **Current CPU cost of the state round trip.** RVM-MobileNetV3's recurrent states at 640x360 with ratio 0.4 are small. Coarse features are computed on a 256x144 image, so r1..r4 total roughly 1 MB (r1 alone is about 16x72x128 f32 = 0.6 MB). That is roughly 4 extract `to_vec()`s plus 4 `clone()`s into new tensors per frame, well under 1 ms on a modern CPU, against 31 ms of inference. Worth fixing for cleanliness (keep the previous `SessionOutputs` values, or use IoBinding with CPU outputs), but don't expect a measurable FPS gain on CPU. This is my estimate; I did not measure it.
- **The same is true of `src` preprocessing.** `to_rgb_f32_nchw` allocates a fresh 640x360x3 f32 `Vec` (about 2.7 MB) every frame. Reusing a buffer, or binding a pre-allocated input tensor and writing into it in place, removes allocator churn. Small, but free.
- **On DirectML, the round trip costs more than the bytes suggest.** Each GPU-to-CPU readback forces a GPU sync and stalls the D3D12 queue. Binding r1o..r4o to DML memory and feeding them back next frame removes 4 readbacks and 4 uploads per frame. Pattern: create two sets of device tensors (ping-pong), bind outputs of set A, run, then bind set A as inputs and set B as outputs next frame. Bind `pha` to CPU memory (`bind_output_to_device` with CPU `MemoryInfo`) so ORT does a single readback. Reset = re-bind zero-filled 1x1x1x1 CPU tensors, as today.
- **Ping-pong and dynamic shapes.** If the RVM model keeps dynamic shapes, the ping-pong needs output shapes known up front. `bind_output_to_device` lets ORT allocate device outputs, so the simplest path is to take the bound outputs from `run_binding` and `bind_input` them next frame.

### Gaps
- No public measurements of DirectML upload/readback latency for tensors of this size. The likely order is sub-ms per transfer, with the sync stall being the real cost, but this is unverified and needs a Windows timing test with `tracing` spans.
- No public Rust or `ort` example of IoBinding with the DirectML EP. The rc.15 doc example uses CUDA. Treat it as compile-checkable but runtime-unverified, which matters given that Windows is test-on-user-PC only.

## 3. DirectML specifics, its maintenance status, and Windows ML as successor

### Takeaway
DirectML works but is in "sustained engineering": it is maintained but frozen for features, and Windows ML labels it "(legacy)". The DML session must have memory pattern disabled and sequential execution. Page2Cam's `runtime.rs` sets neither explicitly. Sequential is the default, but memory pattern is **enabled by default**, and ORT documents an error if it isn't disabled. The DML docs say these must be disabled "or an error is returned". I could not verify ORT 1.24.4's actual behaviour (the ORT source fetch failed; it may instead auto-disable them with a warning), so set both explicitly: it costs nothing and removes the doubt. Windows ML (2.x, through the Windows App SDK / `Microsoft.Windows.AI.MachineLearning` NuGet) is ORT plus a catalog that downloads vendor EPs (QNN, OpenVINO, VitisAI, AMD GPU, TensorRT-RTX) on Windows 11 24H2+. It exposes the standard ORT C API plus a small flat C "EP catalog" API, so a Rust app with `ort`'s `load-dynamic` can in principle use it.

### Cited Findings
- **Status:** "DirectML is in sustained engineering." New feature work has moved to Windows ML. — [ORT DirectML EP](https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html)
- **Required options:** the DML EP "does not support memory pattern optimizations or parallel execution". These "must be disabled or an error is returned". With the C++ API, "execution_mode must be set to ExecutionMode::ORT_SEQUENTIAL, and enable_mem_pattern must be false." Only one thread may call `Run` on a session at a time. — [ORT DirectML EP](https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html)
- **Shapes:** the DML EP works best when "tensor shapes are known at the time a session is created". The docs list fixing the model, `AddFreeDimensionOverrideByName`, or denotation overrides, and cite constant folding, weight pre-processing and DML graph optimization as the benefits. — [ORT DirectML EP](https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html)
- **Adapter choice:** "the primary display (GPU 0) is often not the most performant one". `ort`'s `DirectML` EP has `with_device_id`, `with_performance_preference(HighPerformance|MinimumPower)` and `with_device_filter(Gpu|Npu|Any)`, which map to `SessionOptionsAppendExecutionProvider_DML2` / `OrtDmlDeviceOptions`. — [ORT DirectML EP](https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html); ort rc.15 `ep/directml.rs`
- **What Windows ML is:** "the Windows-supported and maintained copy of ONNX Runtime (ORT)", with "Same ONNX APIs — no changes to your existing ONNX Runtime code". It ships as a shared system component or self-contained, and apps can "dynamically acquire the latest execution providers". NPU and vendor GPU EPs "require Windows 11 version 24H2 (build 26100) or greater"; CPU and DirectML work on all supported versions. The page is dated 2026-11-02. — [What is Windows ML?](https://learn.microsoft.com/en-us/windows/ai/new-windows-ml/overview)
- **EPs included with Windows ML:** CPU and "DirectML (legacy)". Downloaded on demand in Windows ML 2.x: AMD GPU (`AMDGPUExecutionProvider`, min `Microsoft.Windows.AI.MachineLearning` 2.5.96, Adrenalin 24.12.1+), NvTensorRtRtx (RTX 30xx+), OpenVINO (Intel), QNN (Snapdragon X Elite/Plus, NPU driver 30.0.140.0+), VitisAI (AMD; Adrenalin 25.6.3+ with NPU driver 32.00.0203.280+), WebGPU (experimental), MIGraphX (deprecated in favour of AMD GPU EP). The page is dated 2026-11-13. — [Windows ML execution providers](https://learn.microsoft.com/en-us/windows/ai/new-windows-ml/supported-execution-providers)
- **EP selection:** by policy (`SetEpSelectionPolicy`: MAX_PERFORMANCE, PREFER_NPU, MAX_EFFICIENCY, ...) or explicitly (`GetEpDevices` and append). Microsoft recommends starting with explicit selection for predictability. The device list can change at runtime when EPs or drivers update. (Search snippet; page not opened.) — [Select execution providers](https://learn.microsoft.com/en-in/windows/ai/new-windows-ml/select-execution-providers); NVIDIA also notes these device-selection APIs were experimental in ORT 1.23 ([edge-ai-vision / NVIDIA](https://www.edge-ai-vision.com/2025/10/deploy-high-performance-ai-models-in-windows-applications-on-nvidia-rtx-ai-pcs/))
- **C API path (relevant to Rust):** Windows ML's C API has no single "register all certified EPs" call. You enumerate the EP catalog (`WinMLEpCatalog.h`), call `WinMLEpEnsureReady`, get the library path (`WinMLEpGetLibraryPathSize` / `WinMLEpGetLibraryPath`), then call ORT's `RegisterExecutionProviderLibrary`. (Search snippet, page not opened; the snippet was partial and partly from mirror sites, so check the exact function names in `WinMLEpCatalog.h`.) — [Register execution providers](https://learn.microsoft.com/en-in/windows/ai/new-windows-ml/register-execution-providers); WindowsAppSDK-Samples has a WinMLEpCatalog C sample (per search summary, not opened)
- **`ort` support for plugin EPs:** rc.15 has `Environment::register_ep_library(name, path)` (wraps `RegisterExecutionProviderLibrary`), `Environment::devices`, `SessionBuilder::with_devices` and `with_auto_device(AutoDevicePolicy::{PreferCPU, PreferNPU, PreferGPU, MaxPerformance, MaxEfficiency, MinPower})`. — ort rc.15 `environment.rs`, `session/builder/impl_options.rs`
- **No ready-made `ort` integration:** I found no `ort` documentation or release note describing a Windows ML backend. — search over docs.rs/ort and the [pykeio/ort releases](https://github.com/pykeio/ort/releases)

### Inferences
- **Immediate fix for the DML path** (`runtime.rs`): add `.with_memory_pattern(false)?` and `.with_parallel_execution(false)?` to the DirectML builder. If ORT really errors without the first (documented, but unverified for 1.24.4; it may only warn and auto-disable), the code would silently fall back to CPU and log a misleading "DirectML unavailable". Also log the adapter used and expose `with_device_id` / `HighPerformance` in config. On laptops with iGPU+dGPU, GPU 0 is often the iGPU.
- **Run DML on an fp16 or static model**, not the dynamic fp32 one (sections 1 and 5). The GPU benefits most from fixed shapes and fp16.
- **Windows ML from Rust is plausible:** point `ort::init_from` at Windows ML's `onnxruntime.dll`, call the flat `WinMLEp*` C functions through `libloading`/`windows-rs`, then use `register_ep_library` and `with_devices`/`with_auto_device`. Two caveats. First, Windows ML's ORT version must provide the C API version `ort` rc.15 asks for (`api-24`); check Windows ML 2.x's bundled ORT version. Second, bootstrapping the Windows App SDK runtime from an unpackaged Win32 Rust exe needs the bootstrapper (`MddBootstrapInitialize`) or the self-contained deployment. This is meaningful work and untestable from the Linux box, so treat it as a later phase.
- **Without Windows ML**, the existing DirectML NuGet path keeps working ("legacy" but included and maintained), so there's no urgency to migrate for GPU. Windows ML matters only for NPU / vendor-EP access.

### Gaps
- Which ORT version Windows ML 2.x bundles (and so whether `api-24` binds against it) was not confirmed.
- No reports found specifically on RVM with the DirectML EP: correctness of ops, speed, or fallbacks. The obs-backgroundremoval plugin ships `rvm_mobilenetv3_fp32.onnx` with a DirectML build ([PR #545](https://github.com/royshil/obs-backgroundremoval/pull/545), [v0.5.18 notes fixing DirectML](https://obsproject.com/forum/resources/background-removal-virtual-green-screen-low-light-enhance.1260/version/4874/download)), which suggests RVM runs on DML, but I found no published FPS.
- Whether WinML can run in an unpackaged, self-contained (xcopy/zip) app without an MSIX identity was not confirmed. The docs mention self-contained deployment, but I did not read the deployment page.

## 4. NPU options on Windows 11 Copilot+ PCs, and Windows Studio Effects masks

### Takeaway
NPU EPs (QNN for Snapdragon, OpenVINO for Intel Core Ultra, VitisAI for AMD Ryzen AI) come through Windows ML's EP catalog on 24H2+. In practice they need static shapes and usually int8/fp16 QDQ models, which RVM's recurrent and dynamic design makes hard. The selfie model is a much easier NPU candidate but already takes about 1 ms on CPU. Windows Studio Effects does expose a documented background-segmentation **mask** mode via a KS camera property (`KSCAMERA_EXTENDEDPROP_BACKGROUNDSEGMENTATION_MASK`) and per-frame mask metadata (`MF_CAPTURE_METADATA_FRAME_BACKGROUND_MASK`). That is the most promising zero-inference path on Copilot+ PCs, but it only works for cameras the OEM opted into Studio Effects, and Page2Cam's webcam path (nokhwa) would need a Media Foundation capture path to read sample metadata.

### Cited Findings
- **NPU EPs via Windows ML** (VitisAI, QNN, OpenVINO) need 24H2 and specific drivers (see section 3). — [Windows ML execution providers](https://learn.microsoft.com/en-us/windows/ai/new-windows-ml/supported-execution-providers)
- **OpenVINO EP** supports CPU, GPU and NPU. Its CPU target is "Intel® Atom, Core, and Xeon processors" (no AMD mentioned). For NPU, `reshape_input` shape bounds are "required for optimal NPU memory allocation and management". `disable_dynamic_shapes` converts models to static. Model caching goes through the `CACHE_DIR` load_config (the old `cache_dir` is deprecated since ORT 1.23). The recommended distribution is now a plugin EP (`onnxruntime-ep-openvino`, NuGet `Intel.ML.OnnxRuntime.EP.OpenVINO`); the legacy EP is deprecated. — [ORT OpenVINO EP](https://onnxruntime.ai/docs/execution-providers/OpenVINO-ExecutionProvider.html)
- **Studio Effects:** applies to cameras on devices "with a supported NPU" where "the hardware manufacturer must have opted in and installed the Windows Studio Effect driver" (Windows 11 22H2+). Via KS properties any app can "Discover if effects are supported", "Turn effects on or off", and "Access any available metadata". Effects are applied at the camera level, so they affect every app using that camera. Teams uses "Windows Studio's NPU-accelerated background segmentation to apply the background blur/replacement effects". — [Windows Studio Effects overview](https://learn.microsoft.com/en-us/windows/apps/develop/windows-integration/studio-effects) (dated 2026-05-04)
- **Mask mode:** `KSCAMERA_EXTENDEDPROP_BACKGROUNDSEGMENTATION_MASK (0x2)`: "background mask metadata production is enabled in the driver (if possible given the MediaType used ...)". It can be set together with BLUR/SHALLOWFOCUS, and SET takes effect while streaming. Minimum client is Windows 11 22H2. — [KSPROPERTY_CAMERACONTROL_EXTENDED_BACKGROUNDSEGMENTATION](https://learn.microsoft.com/en-us/windows-hardware/drivers/stream/ksproperty-cameracontrol-extended-backgroundsegmentation) (page from 2022/2023, possibly stale)
- **Mask delivery:** the `MF_CAPTURE_METADATA_FRAME_BACKGROUND_MASK` sample attribute carries "a contiguous buffer representing the mask"; "The consuming app is responsible for the scaling and image coordinate correlation of the mask". — [MF_CAPTURE_METADATA_FRAME_BACKGROUND_MASK](https://learn.microsoft.com/en-us/windows/win32/medfound/mf-capture-metadata-frame-background-mask)
- **Microsoft's sample** (C# WinUI/WinRT, `VideoDeviceController.Get/SetDevicePropertyByExtendedId`) lists "Segmentation Mask Metadata" as a capability of the background-segmentation control, but its walkthrough does not show reading the mask per frame. Full functionality needs an NPU, the Studio Effects driver and an opted-in front camera. — [Windows-Camera WindowsStudio sample](https://github.com/microsoft/Windows-Camera/tree/master/Samples/WindowsStudio)
- **Camera support:** Microsoft says Studio Effects now supports compatible third-party cameras. — [Windows Studio Effects support page](https://support.microsoft.com/en-us/windows/ai/ai-features/windows-studio-effects) (via search summary; not opened)

### Inferences
- **For Page2Cam, a Windows-only "NPU mask" engine** works like this: open the webcam with Media Foundation (`IMFSourceReader`), set the KS property to MASK via `IKsControl` (or the WinRT `VideoDeviceController.SetDevicePropertyByExtendedId`), and read `MF_CAPTURE_METADATA_FRAME_BACKGROUND_MASK` from each sample's `MFSampleExtension_CaptureMetadata` attribute store. That gives a mask at near-zero CPU/GPU cost on Copilot+ laptops. It cannot run through nokhwa as used today, and it is untestable from the Linux box. It fits the "self-explaining failure" requirement only if the capability probe is logged. Mask quality is likely coarser than RVM, since it was designed for blur.
- **QNN/VitisAI/OpenVINO-NPU for RVM:** these NPUs generally want static-shape, quantized (QDQ int8 or fp16) graphs. RVM's ConvGRU recurrent state and dynamic Resize from `downsample_ratio` would need a static re-export, quantization and per-vendor validation. High effort with uncertain payoff; not recommended before CPU/DirectML tuning.

### Gaps
- No source confirmed that Studio Effects drivers actually implement the MASK flag (versus only BLUR/SHALLOWFOCUS) on shipping Copilot+ devices, or the mask's resolution and format in practice.
- There is also a Windows AI APIs "image segmentation" / "Image Object Extractor" family in the Windows App SDK (from memory, unverified: Copilot+ only, with packaged-app/identity requirements). I did not research whether it is fast enough for real-time video or callable from unpackaged Rust.
- No public benchmarks of RVM on QNN, VitisAI or OpenVINO NPU.

## 5. Quantization and fp16 (RVM)

### Takeaway
An official `rvm_mobilenetv3_fp16.onnx` exists. Use it for the DirectML path: the GPU benefits, and it avoids building a conversion pipeline. On CPU, fp16 doesn't help (ORT's CPU EP lacks most fp16 kernels on x86). For CPU, the candidate is static int8 QDQ (S8S8) with calibration frames. Zen 4 (8600G) has AVX-512 VNNI, so int8 kernels have hardware support, but MobileNetV3's hard-swish and the GRU gates make quality loss a real risk and the gain unproven. INT8 on DirectML is a poor bet.

### Cited Findings
- **Official RVM ONNX downloads:** `rvm_mobilenetv3_fp32.onnx`, `rvm_mobilenetv3_fp16.onnx`, plus ResNet50 fp32/fp16. "Tested on ONNX Runtime with CPU and CUDA backends. Provided models use opset 12." — [RVM README](https://github.com/PeterL1n/RobustVideoMatting)
- **fp16 input types:** inputs must have a dtype matching the model's precision: "Other inputs must have `dtype` matching the loaded model's precision". So the fp16 model needs f16 `src`, r*i and `downsample_ratio`. — [RVM inference docs](https://github.com/PeterL1n/RobustVideoMatting/blob/master/documentation/inference.md)
- **RVM speed reference (GPU, PyTorch):** RTX 2060 Super FP16 134 FPS at HD (downsample 0.25); GTX 1080 Ti FP32 104 FPS at HD. — [RVM README](https://github.com/PeterL1n/RobustVideoMatting)
- **ORT float16 conversion:** `onnxconverter_common.float16.convert_float_to_float16(keep_io_types=True)` keeps fp32 I/O. "the CPU version of ONNX Runtime doesn't support float16 ops". fp16 can "improve performance on some GPUs". "There may be some accuracy loss". — [ORT float16 docs](https://onnxruntime.ai/docs/performance/model-optimizations/float16.html)
- **ORT int8:** static quantization is recommended for CNNs. "S8S8 with QDQ is the default setting and balances performance and accuracy". "S8S8 with QOperator will be slow on x86-64 CPUs". Speedups need "x86-64 with VNNI" or similar, and "it is not rare to get worse performance on old devices". On AVX2/AVX512 without VNNI, U8S8 can saturate. Run `quant_pre_process()` first. Per-channel quantization can recover accuracy. — [ORT quantization docs](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html)
- **INT8 on DirectML:** NVIDIA's Model Optimizer FAQ says "DirectML backend (ORT-DML) doesn't support 8-bit precision". QDQ needs opset 19+ for its int8 flow. — [NVIDIA Model Optimizer FAQ](https://nvidia.github.io/Model-Optimizer/_sources/support/2_faqs.rst.txt) (a third-party statement; ORT's DML docs neither confirm nor deny it)

### Inferences
- **fp16 on DirectML:** swap in the official fp16 model, or convert with `keep_io_types=True` so the Rust I/O code stays f32. Expect a meaningful speedup on most DX12 GPUs plus half the memory traffic. The quality difference for RVM in fp16 is normally invisible, since the authors benchmark in fp16. Not verified on DML.
- **CPU int8:** Zen 4 supports AVX-512 VNNI (from memory; AMD spec not fetched here, unverified), so ORT's int8 kernels should be fast on the 8600G. MobileNetV3 is depthwise-heavy, where int8 gains are smaller than on dense convs, and the decoder's GRU sigmoid/tanh and the upsampling/refiner are sensitive. Treat int8 as an experiment: quantize the encoder only (`nodes_to_exclude` on decoder/refiner), calibrate on about 200 real webcam frames, and compare alpha edges. Plausible gain is 1.3x to 2x; quality risk is moderate.
- **The ResNet50 RVM variant** is far too heavy for CPU. Ignore it.

### Gaps
- No published CPU int8 benchmarks or quality comparisons for RVM. No published RVM fp16 numbers on DirectML.
- Whether the official fp16 ONNX (opset 12) runs fully on DML, without CPU fallback of some ops, is unverified.

## 6. CPU tricks: resolution, downsample_ratio, lower inference rate, still-frame skipping, ROI

### Takeaway
These algorithmic levers likely give larger CPU wins than any session flag. RVM's cost scales roughly with input pixels. Running RVM at 15 fps and reusing or warping the mask for in-between frames halves CPU. Skipping inference while the frame is static is also cheap. ROI cropping helps the most when the person is small in frame. RVM's recurrence makes skipping and cropping subtler than with stateless models.

### Cited Findings
- **RVM's own guidance on downsample_ratio:** "Set `downsample_ratio` so that the downsampled resolution is between 256 and 512." The table lists 0.375 (portrait) and 0.6 (full-body) for 1280x720, 0.25/0.4 for 1080p, and 1 for inputs at or below 512x512. "higher `downsample_ratio` is not always better". — [RVM inference docs](https://github.com/PeterL1n/RobustVideoMatting/blob/master/documentation/inference.md)
- **RVM's architecture:** the coarse network runs on the downsampled image and a deep-guided-filter refiner upsamples to full input resolution. HD/4K FPS barely differ on GPU (134 vs 108 FPS on an RTX 2060S) because the downsampled size is held roughly constant via `downsample_ratio`. — [RVM README](https://github.com/PeterL1n/RobustVideoMatting)

### Inferences
- **The current setting is already at the coarse floor.** 640x360 x 0.4 = 256x144; the short side is 144, below the 256 to 512 guidance if read per side. If the guidance refers to the long side, it is at the minimum. The encoder is unlikely to get cheaper by lowering the ratio further without quality loss.
- **The full-resolution 640x360 refiner** is the other cost. Try 512x288 with ratio 0.5 (same 256x144 coarse pass, about 36% fewer refiner pixels). Do NOT raise `downsample_ratio` to 1 at 640x360: the coarse network would then run at 640x360, about 6x the pixels of 256x144, which is slower. A cleaner option: run RVM at the coarse size only (for example 384x216 with ratio 1, or keep 256x144) and upsample `pha` with a guided/joint-bilateral filter in the compositor. All of these are measurable by benchmark in an afternoon.
- **Temporal decimation:** run RVM every 2nd frame (15 Hz at 30 fps output) and reuse the last mask. The PIP is small and the person moves slowly, so lag is usually invisible. Mask lag on fast motion shows as edge halos; mitigate by dilating or feathering the reused mask slightly. RVM's recurrent state should tolerate a 15 Hz cadence (unverified, from memory: I believe RVM was trained on video clips at varied frame rates; I did not confirm this from the paper). This should give about 2x lower average CPU and is the biggest cheap win.
- **Async pipelining:** run inference on its own thread with a `FrameSlot` (latest-only), as the app's architecture already does elsewhere, so the compositor never waits. The output then uses the newest finished mask. Combined with decimation, this makes the CPU cost adaptive.
- **Static-scene skip:** compute a cheap difference on a 64x36 grayscale thumbnail. If the mean abs diff is below a threshold, reuse the previous mask (and, for RVM, don't advance recurrent state). Big savings for "talking head, little motion" streams. Force a refresh every N frames.
- **ROI cropping:** use the previous mask's bounding box plus a margin to crop the webcam frame before inference. This gains a lot when the person fills under half the frame. With RVM, changing the crop window changes the spatial size of the recurrent states, so it requires a reset or fixed-size crops (fixed output size, moving window), which breaks temporal consistency on crop moves. Recommended only for the stateless MediaPipe model, or with RVM at a fixed crop size and a slow-moving window.
- **Hybrid:** use MediaPipe (1 ms) every frame for motion/ROI and as a fallback, and run RVM at a lower rate for edge quality. This is complex; consider it only if decimation alone isn't enough.

### Gaps
- The RVM README and inference docs (cited in sections 2, 5, 6 and 8) date from 2021: possibly stale, though the model and ONNX files are unchanged since.
- No published measurements of RVM CPU latency versus input size or downsample_ratio. These need a local benchmark sweep (cheap to write as an ignored test or example).

## 7. OpenVINO EP and XNNPACK EP for these models

### Takeaway
Neither helps the primary dev and test hardware. OpenVINO targets Intel CPU/iGPU/NPU (the 8600G is AMD), and on Windows it now ships as a plugin EP via Windows ML or Intel NuGet. XNNPACK mainly targets Arm/mobile, needs a custom ORT build or package, and its threading model conflicts with ORT's. On x86 it's unlikely to beat MLAS for MobileNetV3. Both are low priority.

### Cited Findings
- **OpenVINO EP:** devices CPU/GPU/NPU; CPU defined as Intel Atom/Core/Xeon. Plugin EP packages (`onnxruntime-ep-openvino`, NuGet `Intel.ML.OnnxRuntime.EP.OpenVINO`) are recommended and the legacy EP is deprecated. It is also distributed via Windows ML (`OpenVINOExecutionProvider`). — [ORT OpenVINO EP](https://onnxruntime.ai/docs/execution-providers/OpenVINO-ExecutionProvider.html); [Windows ML EPs](https://learn.microsoft.com/en-us/windows/ai/new-windows-ml/supported-execution-providers)
- **XNNPACK EP:** optimized "for Arm®-based, WebAssembly, and x86 platforms". It requires building ORT with XNNPACK. Unsupported nodes fall back to the CPU EP. Recommended setup: ORT intra-op threads = 1, spinning disabled, and XNNPACK's own pool sized to physical cores. Ops are limited (2D Conv/Pool; Resize bilinear only; QLinearConv with constant scales). "Performance testing is the best way to determine the optimal configuration". — [ORT XNNPACK EP](https://onnxruntime.ai/docs/execution-providers/Xnnpack-ExecutionProvider.html)

### Inferences
- **`ort` has EP wrappers for OpenVINO and XNNPACK,** but with `load-dynamic` the loaded ORT binary must contain them. The stock Linux `libonnxruntime.so` and the DirectML NuGet don't include them (to my knowledge), so they'd mean shipping extra binaries for marginal gains.
- **Intel users on Windows:** the OpenVINO EP through Windows ML (GPU/NPU) is the realistic way to help them. That's part of the Windows ML effort in section 3, not separate work.

### Gaps
- No RVM or MediaPipe-selfie benchmarks for OpenVINO or XNNPACK EPs were found.

## 8. Ranking by effort vs payoff (synthesis)

### Takeaway
Order of work: (1) fix the DML session options; (2) decimate or async RVM; (3) tune threads and spinning; (4) buffer reuse; (5) fp16 + IoBinding on DML; (6) static re-export; (7) int8 CPU experiment; (8) Studio Effects mask / Windows ML NPU as later Windows-only phases.

### Cited Findings
- DML requires mem pattern off and sequential execution — [ORT DirectML EP](https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html)
- RVM recommends keeping recurrent state on device — [RVM inference docs](https://github.com/PeterL1n/RobustVideoMatting/blob/master/documentation/inference.md)
- Official fp16 RVM ONNX exists — [RVM README](https://github.com/PeterL1n/RobustVideoMatting)
- Spinning trades CPU for latency — [ORT threading](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)
