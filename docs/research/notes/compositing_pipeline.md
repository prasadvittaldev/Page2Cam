# Making Page2Cam's 1080p30 compositing pipeline faster and lower-latency (Windows 11 + Linux, Rust)

Research date: 2026-11-18. Material gathered by web search/fetch plus a read of the Page2Cam source. Statements about Page2Cam's current behaviour cite the source file (local path). Web sources are linked inline. Anything without a source is in **Inferences** or **Gaps**.

Note on effort: about 25 search/fetch calls. Several key numbers (zune-jpeg vs libjpeg-turbo at 720p, jpeg-encoder `simd` speed-up, wgpu readback on iGPUs, D3D11 video processor throughput) were **not found in any published benchmark**. They are listed as gaps, and the cheapest way to fill them is a local `criterion` micro-benchmark (see the measurement section).

---

## 0. Baseline: what the current code does per tick (from source)

### Takeaway
Each 33 ms tick does about 6–8 full-frame (8.3 MB) memory passes and allocations that the work doesn't need. Every per-pixel loop is scalar. The cheapest wins are removing copies and allocations, caching the scaled PIP, and turning on SIMD in crates already in the tree. GPU work is not needed for these.

### Cited Findings
- CEF `on_paint` copies the whole 1920x1080 buffer with `.to_vec()` (a fresh 8.3 MB allocation plus a copy) on every paint and ignores the `_dirty_rects` argument — `/home/prasad/Desktop/Page2Cam/crates/p2c-browser/src/handlers.rs` (lines ~65–79).
- `compose()` copies the page into `out` with `copy_from_slice` every tick, even when the page `seq` hasn't changed. For cut-out styles it also creates a new `Resizer` and a new destination `Image` (heap allocation) every tick, rescales the webcam/matte, and blends with a scalar per-pixel loop that divides by 255 (`(s*a + d*(255-a) + 127) / 255`) — `/home/prasad/Desktop/Page2Cam/crates/p2c-compositor/src/compose.rs`. `fill_black` and `blit` (sets A=255 per pixel) are also scalar.
- `FrameSlot` is a `parking_lot::Mutex<(Option<Arc<Frame>>, u64)>`. `seq()` and `latest()` take the lock separately — `/home/prasad/Desktop/Page2Cam/crates/p2c-core/src/slot.rs`.
- The ticker paces with `std::thread::sleep(deadline - now)` against absolute deadlines and skips missed ticks — `/home/prasad/Desktop/Page2Cam/crates/p2c-compositor/src/ticker.rs`.
- `PreviewSink` does `frame.clone()` (8.3 MB alloc+copy) every Nth frame. The encoder thread **polls every 80 ms**, scales 1920→960 with a new `Resizer`, then JPEG-encodes at quality 70 with `jpeg-encoder` 0.6 — `/home/prasad/Desktop/Page2Cam/crates/p2c-admin/src/preview.rs`. The workspace depends on `jpeg-encoder = "0.6"` **without the `simd` feature** (the crate's `[features]` include `simd = ["std"]`; checked in `~/.cargo/registry/src/*/jpeg-encoder-0.6.1/Cargo.toml`).
- `StreamSink` does `frame.clone()` every tick while live and writes **raw BGRA (8.3 MB/frame ≈ 249 MB/s at 30 fps)** to ffmpeg stdin. ffmpeg args: `-f rawvideo -pix_fmt bgra` input, `-c:v libx264 -preset veryfast -tune zerolatency -pix_fmt yuv420p`, CBR via `-b:v/-maxrate/-bufsize`, GOP = 2 s. So the BGRA→YUV420 conversion happens inside ffmpeg (swscale) — `/home/prasad/Desktop/Page2Cam/crates/p2c-stream/src/controller.rs`, `args.rs`.
- Windows vcam: the app `memcpy`s 8.3 MB of BGRA into the shared-memory seqlock (`p2c_shm::write_frame`). The DLL then copies the frame out again with `p2c_shm::read_frame` (`out.resize` + `copy_nonoverlapping` of 8.3 MB) and converts with `p2c_shm::fill_nv12`/`fill_rgb32` (`/home/prasad/Desktop/Page2Cam/crates/p2c-vcam-win-source/src/win/stream.rs` lines ~223–269). `fill_nv12` is scalar, nearest-neighbour, recomputes the source index through a closure per pixel, and samples chroma from a single pixel (no 2x2 average) — `/home/prasad/Desktop/Page2Cam/crates/p2c-shm/src/layout.rs`, `convert.rs`.
- Linux vcam: scalar `bgra_to_yuyv` into a reused `Vec`, then `write_all` of 4.1 MB to `/dev/videoN` — `/home/prasad/Desktop/Page2Cam/crates/p2c-vcam/src/convert.rs`, `linux.rs`.
- Webcam: requests 1280x720 MJPEG @30 (`Closest`). MJPEG is decoded with zune-jpeg 0.4 to BGRA. YUYV/NV12 go through a scalar per-pixel `yuv_to_bgra` — `/home/prasad/Desktop/Page2Cam/crates/p2c-webcam/src/capture.rs`, `decode.rs`.

### Inferences
- Rough memory traffic per tick with the stream and vcam on: page `to_vec` (read+write 16.6 MB, on the CEF thread) + compose copy (16.6 MB) + stream clone (16.6 MB) + pipe write (8.3 MB read, plus a kernel copy) + shm write (16.6 MB) + DLL read/convert (≥12 MB) + preview clone. That is roughly **100 MB of memory traffic per frame, about 3 GB/s at 30 fps**. An ordinary laptop with dual-channel DDR4/LPDDR5 has tens of GB/s, so this fits, but it competes with CEF, the iGPU (shared memory), and ONNX segmentation. Each avoided 8 MB copy is worth roughly 0.3–1 ms of one core. These figures are my arithmetic, not measurements.
- The likely CPU hot spots, in order: (1) CEF software paint plus the `to_vec` copy, (2) MJPEG decode, (3) libx264 `veryfast` 1080p30 encode inside ffmpeg (separate process; not profiled, so its rank is a guess), (4) scalar BGRA→NV12/YUYV, (5) preview downscale plus JPEG encode, (6) PIP rescale plus blend (small, because the PIP covers only part of the frame).

### Gaps
- No profile has been run on real hardware. Step 1 should be per-stage `Instant` timing in the ticker (compose, each sink's `push`) logged as p50/p99, plus `cargo flamegraph`/`samply` on Linux and Windows.

## 1. CPU-side optimisations (SIMD, caching, copies, colour conversion)

### Takeaway
Ranked by effort vs payoff: (a) stop copying and allocating 8 MB buffers (reuse buffers, compose only when inputs change, write straight into the shm/pipe buffer); (b) cache the scaled PIP by `(cam.seq, matte.seq, w, h)` and reuse one `Resizer`; (c) replace the scalar colour converters with `yuvutils-rs` (AVX2/SSE/NEON, BSD-3/Apache-2.0, roughly libyuv speed); (d) SIMD the blend with premultiplied alpha and the `*0x8081>>23` divide-by-255 trick, or let `std::simd`/`wide` auto-vectorise a branch-free loop; (e) send NV12/I420 instead of BGRA to ffmpeg. Dirty-rectangle compositing helps CEF most, by not copying unchanged regions.

### Cited Findings
- **fast_image_resize** (already used) has SSE4.1/AVX2/NEON paths. Its benchmark (AMD Ryzen 9 5950X, fast_image_resize 6.0.1, single-thread) for RGBA8 bilinear downscale 4928x3279→852x567 reports **rust 26.01 ms, SSE4.1 13.18 ms, AVX2 10.21 ms**, vs the `resize` crate 88.03 ms and libvips 137.35 ms. That figure includes "multiply by alpha => resize => divide by alpha". It has an optional `rayon` feature — [fast_image_resize benchmarks-x86_64.md](https://github.com/Cykooz/fast_image_resize/blob/main/benchmarks-x86_64.md); [README](https://github.com/Cykooz/fast_image_resize). Page2Cam's workspace asks for `fast_image_resize = "5"` (5.5.0 is what's in the local cargo registry; `Cargo.lock` not checked). The benchmark used 6.0.1.
- **yuvutils-rs**: "Mostly implemented AVX-512, AVX2, SSE, NEON, WASM" with runtime feature detection. The README says all methods support RGB/BGR/BGRA/RGBA and lists YCbCr, YCgCo, YUY2, Identity and Sharp YUV. The docs.rs index (v0.8.3) has `bgra_to_yuv_nv12` (BGRA→NV12), `yuv_nv12_to_bgra` and `yuyv422_to_bgra`, but **no direct BGRA→packed-YUYV function was listed**. For v4l2loopback you'd likely go BGRA→planar 4:2:2 then pack, or keep a hand-SIMD packer (to verify) — [docs.rs yuvutils-rs](https://docs.rs/yuvutils-rs/latest/yuvutils_rs/). Its benchmark for RGBA→YUV 4:2:0 on a 1997x1331 image gives **781.54 µs (AVX2) vs libyuv 846.69 µs; 367.47 µs (AVX2, Windows) vs libyuv 2.70 ms; 257.02 µs NEON vs 429.36 µs**. NV12→RGBA decode is 917.52 µs AVX2 / 359.11 µs AVX2-Windows. AVX-512 needs nightly. Licence BSD-3-Clause or Apache-2.0. Pure Rust, so it cross-compiles with cargo-xwin, unlike libyuv (C++) — [yuvutils-rs README](https://github.com/awxkee/yuvutils-rs).
  - 1920x1080 is 2.07 MP vs 2.66 MP for 1997x1331 (0.78x). Scaled down, that is roughly **0.3–0.6 ms per BGRA→NV12 frame**. This is my extrapolation.
- **SIMD alpha blending**: no clean published AVX2-vs-scalar blend benchmark was found. Related numbers: the `garb` crate reports an RGBA↔BGRA swizzle at 150 µs vs 1,078 µs naive (7.2x, Zen 4). The `simd-blend-modes` project shows 1.3x–2.2x AVX2 vs scalar C kernels on 256x256 blend modes. (Search-snippet level; pages not fetched:) a Stack Overflow answer gives the AVX2 divide-by-255 as `_mm256_mulhi_epu16(x, 0x8081) >> 7` — [SO mirror](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/58459575/avx2-simd-instrinsics-16-bit-to-8-bit-vice-versa). The `pic-scale` crate has an `avx2_div_by255` helper — [pic-scale alpha_u8.rs](https://docs.rs/crate/pic-scale/0.7.7/source/src/avx2/alpha_u8.rs). An FFmpeg patch discussion uses `(src*a + dst*(255-a) + 255) >> 8` — [patchwork.ffmpeg.org](https://patchwork.ffmpeg.org/comment/31829); [garb](https://docs.rs/crate/garb/0.2.5); [simd-blend-modes](https://pypi.org/project/simd-blend-modes/).
- **zune-jpeg** "heavily relies on platform specific intrinsics, namely AVX2 and SSE". The intrinsics "perform poorly in debug builds", and decoding is single-threaded — [zune-jpeg README](https://github.com/etemesi254/zune-image/tree/dev/crates/zune-jpeg). (Page2Cam has both zune-jpeg 0.4.21 and 0.5.15 in the registry; the webcam crate uses 0.4.)

### Concrete techniques (ranked: effort → payoff) — these are inferences/recommendations built on the findings above and the source read, not cited facts
1. **Low effort, high payoff: remove 8 MB clones and allocations.**
   - `StreamSink`/`PreviewSink`: compose into an `Arc<Frame>` taken from a small pool of 3 buffers (triple buffering) and hand the `Arc` to sinks instead of `frame.clone()`. A sink that needs the frame later keeps the `Arc`. The ticker takes a free buffer from the pool for the next tick, or reuses the oldest if a sink still holds one, which drops that frame for the slow sink.
   - CEF `on_paint`: reuse a buffer from a pool instead of `to_vec`. Better, copy only `dirty_rects` into a persistent page buffer, then publish.
   - Ticker: skip `compose_page` when the page `seq` and the PIP inputs are unchanged and the layout is the same. Re-emit the previous `out` (sinks still get a frame each tick for the vcam's sake).
   - Reuse one `Resizer` and one destination `Image` per call site (`Resizer` holds internal buffers; the README examples create it per call, but it is a reusable struct).
2. **Low effort: cache the scaled PIP** keyed on `(cam_seq, matte_seq, w, h, style)`. The webcam updates at ≤30 fps and the matte often slower. When neither changed, skip both the rescale and the alpha-to-premultiplied step.
3. **Low effort: enable `jpeg-encoder`'s `simd` feature** (AVX2 only; the README says the `simd` feature "implies std and only AVX2 as for now" — [jpeg-encoder](https://github.com/vstroebel/jpeg-encoder)). (It already encodes 4:2:0: `Encoder::new` picks 2x2 subsampling for quality < 90, and Page2Cam uses 70 — `jpeg-encoder-0.6.1/src/encoder.rs` line ~219–238.) Make the preview thread wait on a notification instead of polling.
4. **Medium effort: yuvutils-rs** for BGRA→NV12 (Windows DLL, `bgra_to_yuv_nv12`) and YUYV/NV12→BGRA (webcam). For BGRA→YUYV (Linux v4l2loopback) a direct function wasn't found, so verify or SIMD the existing packer. This replaces three scalar loops. It also fixes chroma quality in the DLL (current NV12 chroma is point-sampled from one pixel).
5. **Medium effort: move the conversion to the producer side for the Windows camera.** Write NV12 (3.1 MB) into the shm instead of BGRA (8.3 MB) and let the DLL copy it straight into the MF sample buffer, honouring pitch. This needs a shm protocol version bump. Keep RGB32 as a slower fallback path, or convert NV12→RGB32 in the DLL only when the client asks for RGB32.
6. **Medium effort: send YUV to ffmpeg.** Use `-pix_fmt nv12` or `yuv420p` on the rawvideo input, converted once with yuvutils-rs. That is 3.1 MB/frame instead of 8.3 MB through the pipe, and ffmpeg's swscale step goes away. If the same NV12 buffer is shared with the vcam, the conversion is done once for both sinks.
7. **Medium effort: SIMD blend.** Premultiply the PIP once when it is (re)scaled (cached, see #2). The per-tick blend then becomes `d = s + d*(255-a)/255`: one multiply per channel instead of two. Write it as a branch-free loop over `u16x16` with `wide` or `std::simd`. (`std::simd` is still nightly-only, so `wide` or hand-written `core::arch` AVX2 with runtime detection is the stable route.) The PIP area at 25% width is about 0.1 MP, so even scalar it is small. This ranks below #1–#6.
8. **Higher effort: dirty-rect compositing** end to end (CEF dirty rects → page buffer → output → vcam conversion of the changed rows only). It pays off when the page is mostly static, which is common for slides and dashboards. It adds complexity in every sink. YUYV/NV12 conversion of only the changed rows is easy, and the x264 path still takes full frames.

### Inferences
- Items 1–3 together probably cut CPU time per frame by several milliseconds and much of the memory traffic, with no new dependencies except a feature flag. This is my estimate; measure before and after.
- yuvutils-rs is the best fit for cross-compiling from Linux with cargo-xwin (pure Rust). libyuv bindings need a C++ toolchain per target, and `dcv-color-primitives` (AWS, Rust, BGRA→NV12 with SSE/AVX2) is an alternative I did not benchmark here.

### Gaps
- No published apples-to-apples benchmark of an AVX2 BGRA "over" blend vs scalar in Rust. No published `dcv-color-primitives` vs yuvutils-rs comparison was retrieved.
- No published speed figure for `jpeg-encoder`'s `simd` feature or a turbojpeg-vs-jpeg-encoder comparison. The `turbojpeg` crate needs libjpeg-turbo (C/NASM), which complicates the Windows cross-build.

## 2. GPU compositing in Rust (wgpu, D3D11) and zero-copy paths

### Takeaway
At 1080p30 with a CPU-sourced page (software `OnPaint`) and CPU sinks (shm, v4l2loopback, ffmpeg pipe), a GPU compositor adds an upload (8 MB) and a readback (3–8 MB) per frame and at least a frame of pipelining. On integrated GPUs (UMA) bandwidth is not the bottleneck, but sync and latency are. **The GPU only pays off if frames stay on the GPU end to end.** That means CEF shared textures (`OnAcceleratedPaint`) → GPU composite → NV12 → a hardware encoder and/or D3D samples for the virtual camera. That is a large, Windows-specific project. Do the CPU items first.

### Cited Findings
- **CEF shared-texture OSR** (older material: the original PR is years old, and cef-mixer targets Chromium 120, i.e. ~2023): with `shared_texture_enabled` set, CEF calls `OnAcceleratedPaint` instead of `OnPaint` when Chromium can create a shared D3D11 texture — [CEF PR #158 "Support external textures in OSR mode"](https://bitbucket.org/chromiumembedded/cef/pull-requests/158). The cef-mixer sample says D3D11 shared textures "improve the OSR rendering performance" but gives no numbers (it targets Chromium 120) — [cef-mixer](https://github.com/twobrainsgmbh/cef-mixer).
- **The Rust `cef` crate** has an `osr_texture_import` module behind the `accelerated_osr` feature. **Verified locally:** the pinned `cef-156.6.0+156.0.30` has `src/osr_texture_import/{d3d11,dmabuf,vulkan,iosurface,shared_texture_handle,common}.rs` and an `accelerated_osr` feature (pulls in `ash`, `wgpu`, `windows`, ...). Page2Cam builds `cef` with `default-features = false`, so it is off today. (A search snippet called the Linux flag `accelerated_paint_dmabuf`; the pinned Cargo.toml has no such feature, only `accelerated_osr`.) It copies CEF's shared texture into an application-owned `wgpu::Texture`: **Windows via D3D11 shared textures through D3D12 or Vulkan interop, Linux via DMA-BUF through Vulkan external memory**. It needs `wgpu::Features::VULKAN_EXTERNAL_MEMORY_DMA_BUF` / `VULKAN_EXTERNAL_MEMORY_WIN32`. `import_to_wgpu` must be called "within the originating `on_accelerated_paint` callback", "waiting for GPU completion", on the same physical GPU/driver as CEF — [cef crate osr_texture_import/mod.rs](https://docs.rs/crate/cef/latest/source/src/osr_texture_import/mod.rs). (The fetched docs.rs page was cef 148.x; the module files exist in 156.6.0, but the API was not diffed.)
- A third-party CEF/GTK4 bridge treats DMA-BUF as primary on Linux and software OnPaint as a "diagnostic fallback". It notes that shared-texture OSR builds can report a fractional `device_scale_factor` while emitting 1x DMABUF frames — [purego-cef2gtk](https://pkg.go.dev/github.com/bnema/purego-cef2gtk@v0.8.4). I found no official CEF documentation of the Linux `OnAcceleratedPaint` payload.
- **wgpu readback** (search-snippet level for Bevy/luma.gl wording): no 1080p iGPU benchmark was found. Engines that use it (Bevy, rerun `re_renderer`) schedule the copy in one frame and collect it in a later frame because `map_async` resolves only after `poll()`, so readback is "always a frame of latency". luma.gl notes that reusing one buffer forces a wait — use a ring of staging buffers — [Bevy gpu_readback.rs](https://dev-docs.bevyengine.org/src/gpu_readback/gpu_readback.rs.html); [re_renderer texture_readback.rs](https://docs.rs/crate/re_renderer/0.32.1/source/src/texture_readback.rs); [luma.gl GPU memory](https://luma.gl/docs/api-guide/gpu/gpu-memory).
- **wgpu has no D3D11 backend** (search-snippet level, ~2023–24 change; page not fetched). It was removed (PR #4828, "Remove DX11 backend") because it "had no functionality" and desktop GL now covers older hardware. Backends are DX12/Vulkan/Metal/GL — [wgpu changelog (via mirror)](https://github.com/SecondHalfGames/wgpu/blob/trunk/CHANGELOG.md); [Mozilla bug 1868672](https://bugzilla.mozilla.org/show_bug.cgi?id=1868672).
- **Windows Media Foundation virtual camera with GPU samples:** VCamSample (which Page2Cam's DLL ports) creates frames "on the GPU, if a Direct3D manager has been provided by the environment" ("the case of the Windows 11 camera app"), otherwise on the CPU. Teams/Chrome/Edge ImageCapture are given as "D3D-less" environments. On the GPU path, NV12 conversion uses "Media Foundation's Video Processor MFT" — [VCamSample README](https://github.com/smourier/VCamSample). D3D11 texture samples come from `IMFVideoSampleAllocatorEx` (set `MF_SA_D3D11_USAGE`/`MF_SA_D3D11_BINDFLAGS` and the `IMFDXGIDeviceManager`) — [IMFVideoSampleAllocatorEx](https://learn.microsoft.com/windows/win32/api/mfidl/nn-mfidl-imfvideosampleallocatorex). Existing textures can be wrapped with `MFCreateDXGISurfaceBuffer` — [MFCreateDXGISurfaceBuffer](https://learn.microsoft.com/en-au/windows/win32/api/mfapi/nf-mfapi-mfcreatedxgisurfacebuffer).
- **D3D11 video processor** (`ID3D11VideoDevice::CreateVideoProcessor`, `ID3D11VideoContext::VideoProcessorBlt`) writes processed output (format conversion, scaling) to a D3D surface — [VideoProcessorBlt](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11videocontext-videoprocessorblt). Community reports include blurred NV12 output with some setups — [MS Q&A](https://learn.microsoft.com/en-us/answers/questions/1192424/videoprocessor-render-nv12-format-texture2d-have-w). GStreamer's `d3d11convert` is an open-source production user — [GStreamer d3d11convert](https://gstreamer.freedesktop.org/documentation/d3d11/d3d11convert.html).

### Inferences
- Because the Frame Server loads the DLL in a **different process** (svchost), our app's GPU texture can't simply be handed over. It would need a shared NT handle (`IDXGIResource1::CreateSharedHandle` → `ID3D11Device1::OpenSharedResource1` in the DLL) plus a keyed mutex or fence, and the handle must be duplicated into the service process. Also, the D3D manager is only provided by some clients (Camera app), not Teams/Chrome. So the CPU NV12 path in the shm must remain the main path anyway. **A GPU path for the virtual camera is high effort, unverifiable from this Linux box, and helps only some clients.** I don't recommend it near term.
- A GPU compositor is most worth it where the output is consumed on the GPU: the H.264 encoder (QSV/AMF/NVENC/MF via D3D11 textures, VA-API surfaces) and the admin preview. With the current ffmpeg-child design, frames go through a pipe, so the encoder can't take GPU surfaces. That would require linking libav* (ffmpeg-next) or calling MF/VA-API directly.

### Gaps
- No measured numbers for 1080p upload/readback cost on Intel Iris Xe / AMD Radeon 680M iGPUs with wgpu.
- Whether Windows Frame Server ever provides an `IMFDXGIDeviceManager` to a virtual camera source when Teams is the client is undocumented. VCamSample says it doesn't for Teams/Chrome.

## 3. Webcam decode (MJPEG, raw formats, hardware decode)

### Takeaway
At 720p30, MJPEG decode with zune-jpeg (AVX2) is likely a few ms per frame on a laptop core, which is acceptable. The bigger wins are (a) decode to YCbCr/planar and convert only once at the PIP size, or decode at reduced size; (b) prefer uncompressed NV12/YUY2 when the camera offers it at the wanted resolution and fps (many cameras only offer 720p30+ as MJPEG over USB 2); (c) build release builds of the webcam crate even in dev (SIMD intrinsics are slow in debug). Hardware MJPEG decode (MF hardware MFT, VA-API) exists but has a poor reliability record and adds a copy-back, so it isn't worth it for a 720p PIP.

### Cited Findings
- zune-jpeg aims to "almost match libjpeg-turbo speeds", "always +- 10 ms" of it. It is single-threaded, uses AVX2/SSE intrinsics, and performs poorly in debug builds — [zune-jpeg README](https://github.com/etemesi254/zune-image/tree/dev/crates/zune-jpeg). Its own benchmark file uses a single 7680x4320 image on a Ryzen 5 4500U, with numbers only in an external criterion report — [zune-jpeg Benches.md](https://docs.rs/crate/zune-jpeg/0.4.21/source/Benches.md). A third-party decoder (zenjpeg) reports 1.6–1.8x faster than zune-jpeg on progressive files. Webcam MJPEG is baseline, so this is mostly irrelevant — [zenjpeg](https://github.blesdmm.dns-dynamic.net/imazen/zenjpeg) (mirror; treat with caution).
- Media Foundation (search-snippet level of Microsoft Learn pages): by default the source reader "do[es] not use hardware decoders or encoders". Set `MF_READWRITE_ENABLE_HARDWARE_TRANSFORMS` = TRUE to allow hardware MFTs. DXVA needs `MF_SOURCE_READER_D3D_MANAGER`. `MF_SOURCE_READER_ENABLE_ADVANCED_VIDEO_PROCESSING` adds colour conversion and resizing — [MF_READWRITE_ENABLE_HARDWARE_TRANSFORMS](https://learn.microsoft.com/en-us/windows/win32/medfound/mf-readwrite-enable-hardware-transforms); [Source Reader Attributes](https://learn.microsoft.com/en-ca/windows/win32/medfound/source-reader-attributes).
- An Intel forum report says Intel's hardware MJPEG MFT (`mfx_mft_mjpgvd_64.dll`) broke Store camera apps, with the workaround of disabling hardware decoders in the registry. Another report says the Intel MJPEG MFT is asynchronous (you must implement the async model yourself). These are older, anecdotal reports — [Intel community thread](https://community.intel.com/t5/Media-Intel-Video-Processing/MJPEG-decode-fails-on-Windows-app-store-Camera-applications/m-p/971920); [SO mirror](https://windows-hexerror.linestarve.com/q/so42028159-how-to-use-intel-hardware-mjpeg-decoder-mft-in-mediafoundation-sourcereader-for-window-desktop-appli).
- VA-API JPEG (older forum material, ~2016–2021; a related GStreamer thread is from 2020): one Intel forum user saw the iHD driver take 19 s vs 2.9 s for i965 on a `vaapijpegdec` batch test. Others discuss the cost of copying hardware-decoded frames back to system memory — [Intel forum](https://community.intel.com/t5/Media-Intel-Video-Processing/Performance-of-copy-to-system-memory-after-hardware-decoding/td-p/1244544). A vendor doc says cameras that provide raw formats (NV12/YUY2) "achieve much better results than JPEG/MJPEG cameras" — [Proximie VAAPI doc](https://proximie.github.io/sdk-docs/guide/sdk-features/hardware-encoders/vaapi-h264.html).

### Inferences
- The PIP is typically ≤25% of the output width (≈480 px). Decoding 1280x720 then scaling down wastes work. Two options: request 640x480/640x360 when the PIP is small, or use JPEG DCT scaling (libjpeg-turbo can decode at 1/2 and 1/4 scale; I did not confirm whether zune-jpeg exposes DCT-domain scaling). Cut-out mode needs segmentation input anyway, at a small size.
- Decoding MJPEG to YCbCr and doing YUV→BGRA plus scaling in one pass saves a full-res BGRA buffer. Only worth it after profiling shows decode matters.

### Gaps
- No found benchmark of zune-jpeg vs libjpeg-turbo on 720p/1080p 4:2:2 webcam MJPEG. Expect single-digit ms on a modern laptop core; benchmark locally.

## 4. JPEG preview (cheaper encoders, resolution/fps, WebCodecs/H.264)

### Takeaway
The preview is an operator monitor, not output. Cheap fixes: turn on `jpeg-encoder/simd`, use 4:2:0, encode at 640–960 px wide, cap at 10–15 fps, encode only while a client is connected (already done), wake on new frames instead of polling, and reuse the scaled buffer. WebCodecs H.264 to the browser would cut bandwidth and CPU, but needs an H.264 encoder in-process, a secure context, and careful bitstream setup for 1-in-1-out decoding. Not worth it for a localhost preview.

### Cited Findings
- `jpeg-encoder`: the `simd` feature enables SIMD (AVX2 only) — [jpeg-encoder](https://github.com/vstroebel/jpeg-encoder). I found no published speed comparison against turbojpeg.
- A Raspberry Pi comparison found TurboJPEG fastest among the libraries tested (jpeg-encoder not included) — [jpeg-encoding-performance](https://github.com/codeTom/jpeg-encoding-performance).
- WebCodecs: `optimizeForLatency` is a hint. Whether H.264 decodes 1-in-1-out "depends on how the bitstream is set up" (Chromium bug 1352442). A developer streaming H.265 over WebSocket saw output queued until flush — [w3c/webcodecs#698](https://github.com/w3c/webcodecs/issues/698). A DEV post reports 267 ms → 2.5 ms decode-to-present after fixing SPS issues, and notes WebCodecs needs a secure context — [DEV Community](https://dev.to/joduchan/we-switched-simulator-streaming-to-h264-and-it-felt-worse-heres-how-we-fixed-the-latency-pk9). (`http://127.0.0.1` counts as a potentially trustworthy origin in browsers, so the admin page qualifies. This is my knowledge, not from the retrieved sources.)

### Inferences
- 960x540 at 4:2:0 is about 0.5 MP. At 12.5 fps (the current 80 ms poll) the CPU cost is modest. The scale step plus the 8 MB clone may cost as much as the encode itself. Reusing a `Resizer`, scaling directly from the pooled `Arc<Frame>`, and enabling SIMD is the low-effort win.
- If an in-process GPU H.264 encoder is ever added for RTMP, the same encoder could feed a WebCodecs preview later.

### Gaps
- No numbers for the jpeg-encoder SIMD speed-up.

## 5. Threading, pacing and latency measurement

### Takeaway
The architecture (latest-only slots, absolute-deadline ticker, bounded rings) is already right for low latency. Improvements: make handoffs allocation-free with a buffer pool or triple buffer; replace polling (preview 80 ms sleep) with condvar/`watch` notifications; give the ticker a high-resolution timer on Windows and raise its priority. Measure glass-to-glass with a visible timestamp, or with an LED/photodiode for precision.

### Cited Findings
- Glass-to-glass methods (older material, 2015–16, still the standard reference; search-snippet level): an LED plus phototransistor reference design (Bachhuber & Steinbach) reports 0.5 ms precision at 2 kHz sampling, and the hardware is open source — [arXiv 1510.01134](https://ar5iv.labs.arxiv.org/html/1510.01134); [G2GDelay](https://github.com/cbachhuber/G2GDelay). The simplest method is to film a clock and photograph it next to the receiving display — [bloggeek glass-to-glass](https://bloggeek.me/webrtcglossary/glass-to-glass/). A GStreamer discussion covers tracer-based measurement and its pitfalls — [GStreamer discourse](https://discourse.gstreamer.org/t/measuring-glass-to-glass-latency/2357).

### Inferences
- **Pipeline-only latency** (excluding camera and display) can be measured in software. Have the test page draw `performance.now()`/a frame counter as a barcode or large digits, read it back at each sink (vcam shm, ffmpeg input, preview), and log the delta against a timestamp stamped when CEF's `on_paint` delivered it. Page2Cam already stamps `time_ms` into the shm header (`/home/prasad/Desktop/Page2Cam/crates/p2c-shm/src/layout.rs`). Adding a capture timestamp to `Frame` (CEF paint / webcam capture time) and logging `now - capture` at each sink gives per-stage latency with no hardware.
- Worst-case added latency from a latest-only slot sampled by a fixed 33 ms ticker is up to one tick (≈33 ms) plus compose time. Waking the ticker on a new page frame (or aligning ticks to CEF's `windowless_frame_rate`) cuts that, at the cost of jitter. Configuring CEF's frame rate to 30 and keeping the fixed ticker is a reasonable middle ground.
- Windows timer resolution: `std::thread::sleep` on Windows historically had ~15.6 ms granularity unless the timer resolution was raised. I believe recent Rust std uses a high-resolution waitable timer, but this was **not verified in this research**. Log actual tick intervals on the user's Windows PC (p99 of tick period) to check.
- `FrameSlot`: a mutex held for a pointer swap is fine at 30 fps. An `arc-swap`/`triple_buffer`-style lock-free swap is optional polish. The bigger issue is the allocation per `put`, not the lock.

### Gaps
- Not verified whether Rust std's Windows `sleep` uses `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION` in the toolchain Page2Cam uses.

## 6. GPU when available, with automatic CPU fallback (end-to-end design)

### Takeaway
Keep the CPU path as the reference implementation and always-available fallback. Add a GPU backend behind a `Compositor` trait, tried at startup and on device loss. Build it in the order that pays off first. (1) Hardware **H.264 encode** for RTMP: the biggest CPU consumer (libx264), and it can be done with ffmpeg flags today (`h264_qsv`/`h264_amf`/`h264_nvenc`/`h264_mf`/`h264_vaapi`) by probing at startup and falling back to libx264. (2) GPU colour conversion plus compositing feeding that encoder in-process. (3) CEF `OnAcceleratedPaint` zero-copy input. (4) GPU segmentation I/O sharing (DirectML). (5) GPU virtual camera samples, last, given the cross-process and client-support issues. wgpu (DX12/Vulkan/GL) is the most practical cross-platform API and cross-compiles with cargo-xwin as pure Rust. D3D11 via `windows-rs` is the right tool only for the Windows video-processor and MF/encoder interop bits.

### Cited Findings (with design notes)
The sub-sections below mix cited facts (with links) and design recommendations. Statements tagged **[prior knowledge, not retrieved]** come from general knowledge, not from a page fetched in this session. Verify them before relying on them.

#### (1) Which stages can move to the GPU, and in what order
| Order | Stage | GPU mechanism | Payoff | Effort / risk |
|---|---|---|---|---|
| 1 | **H.264 encode (RTMP)** | ffmpeg hardware encoders (search-snippet level, third-party gists). NVENC low-latency tunes `ll/llhq/llhp`, `-zerolatency 1`. AMF `usage ultralowlatency/lowlatency`. QSV `low_power`. VAAPI `-delay` — [search summary of ffmpeg encoder options (third-party gists)](https://gist.github.com/Brainiarc7/26f15a7f6f316e4ecae2c008b99880e1); [ffmpeg amfenc_h264.c](https://code.ffmpeg.org/FFmpeg/FFmpeg/src/commit/c6c54943d161812b3c4034116cb14f3f5c05dc43/libavcodec/amfenc_h264.c) | Likely the largest CPU saving: libx264 `veryfast` at 1080p30 is probably the heaviest stage (inference; not profiled). Only active while streaming. | **Low.** Change args, probe `ffmpeg -encoders` and do a 1-second test encode at startup, fall back to libx264. Frames still go over the pipe as NV12. |
| 2 | **BGRA→NV12 + downscale for preview/vcam/encoder** | wgpu compute shader, or D3D11 `VideoProcessorBlt` on Windows | Saves ~1 ms/frame of CPU per sink (yuvutils-rs makes CPU cheap too) | Medium. Only worth it once compositing is on the GPU. |
| 3 | **Compositing (page + PIP blend, matte upscale)** | wgpu render/compute pass: two textures in, one out. Matte upscale with a bilinear sampler, or a guided-filter refine (box filters = separable compute passes; unsourced, see Gaps) | Modest at 1080p30 if the page arrives from the CPU (upload 8 MB + readback). Large if the page arrives as a GPU texture (step 4). Guided-filter refinement of a low-res matte is much cheaper on the GPU than on the CPU. | Medium. |
| 4 | **Page input zero-copy** | CEF `shared_texture_enabled` → `OnAcceleratedPaint` → `cef::osr_texture_import` into wgpu (Windows D3D11→D3D12/Vulkan, Linux DMA-BUF→Vulkan) — [cef osr_texture_import](https://docs.rs/crate/cef/latest/source/src/osr_texture_import/mod.rs) | Removes CEF's software raster readback and the 8 MB `to_vec`. Probably the single biggest CPU saving after the encoder. | Medium–high. Import must happen inside the callback and waits for GPU completion. Same GPU as CEF (hybrid-GPU laptops!). |
| 5 | **Webcam decode** | MF source reader with `MF_READWRITE_ENABLE_HARDWARE_TRANSFORMS` + `MF_SOURCE_READER_D3D_MANAGER`. VA-API JPEG on Linux | Small for a 720p PIP | High risk (driver bugs reported above). Prefer requesting NV12/YUY2 from the camera, and CPU zune-jpeg. |
| 6 | **Segmentation (cut-out) on GPU** | (search-snippet level) ONNX Runtime DirectML EP with D3D12 resources bound via IO binding (`CreateGPUAllocationFromD3DResource`). DirectML needs **buffers, not textures**, and does no resource barriers for you — [ORT device tensors](https://onnxruntime.ai/docs/performance/device-tensor.html); [DirectML barriers](https://learn.microsoft.com/en-us/windows/ai/directml/dml-barriers). Importing D3D12 shared handles as zero-copy tensors for plugin EPs is still a **feature request** — [onnxruntime#26821](https://github.com/microsoft/onnxruntime/issues/26821) | Keeps the model input (small, e.g. 256x256) and matte output on the GPU. Saves little bandwidth (tiny tensors), mostly sync. | High. The device must be D3D12, which matches wgpu's DX12 backend (wgpu-hal can expose the raw `ID3D12Device`), but not a D3D11 pipeline. Copying a 256x256 tensor via the CPU costs ~nothing, so do this last. |
| 7 | **JPEG preview** | Downscale on GPU (step 2), keep the CPU JPEG encode (or MF/VA-API JPEG encoder) | Small | Low once step 2 exists. |
| 8 | **Virtual camera D3D samples** | NV12 D3D11 texture shared via NT handle into the Frame Server DLL, `MFCreateDXGISurfaceBuffer`/`IMFVideoSampleAllocatorEx` | Only for clients that give a D3D manager (Camera app, not Teams/Chrome per VCamSample) — [VCamSample](https://github.com/smourier/VCamSample) | Very high, can't be tested from Linux. Skip. Keep NV12-in-shm (CPU) as the only path. |

#### (2) Rust API options
- **wgpu** (DX12 / Vulkan / GL; **no D3D11 backend**, it was removed — [wgpu changelog](https://github.com/SecondHalfGames/wgpu/blob/trunk/CHANGELOG.md)). It is pure Rust plus system drivers, so it **cross-compiles with cargo-xwin** without extra C toolchains. WGSL shaders compile at runtime via naga, so no fxc/dxc is needed at build time (DX12 uses the DXC or FXC runtime DLLs; check whether the dynamic `dxcompiler.dll` must ship, as wgpu can fall back to FXC) **[prior knowledge, not retrieved]**. It already integrates with the CEF crate's `osr_texture_import`. **The most practical choice.**
- **D3D11 via `windows-rs`** **[prior knowledge, not retrieved, except VideoProcessorBlt docs cited in section 2]**: needed for `ID3D11VideoProcessor` (hardware scaling and colour conversion on the fixed-function video engine), MF encoder/sample interop, and `IMFDXGIDeviceManager`. It also cross-compiles with cargo-xwin (bindings only). HLSL shaders would need to be precompiled (fxc is not on Linux; use `naga`/`wgsl` → HLSL ahead of time or ship DXBC blobs), or avoided entirely by using only the video processor. Use it narrowly for Windows interop.
- **Vulkan via `ash`** **[prior knowledge, not retrieved]**: maximum control (Vulkan Video, DMA-BUF import/export, VA-API interop on Linux), but much more code. It is also what wgpu uses underneath on Linux. Prefer wgpu plus `wgpu-hal` escape hatches.
- **Interop glue:** CEF's D3D11 shared texture → wgpu goes through D3D12 (`OpenSharedHandle`) or Vulkan `VK_KHR_external_memory_win32`, as the cef crate does.

#### (3) GPU detection and graceful fallback
- Startup: try to create the GPU backend (wgpu `request_adapter` with `force_fallback_adapter: false`). Reject software adapters **[prior knowledge, not retrieved]** (wgpu reports `DeviceType::Cpu` for WARP/llvmpipe/lavapipe; a GPU path on a software adapter is slower than the CPU path). Run a **self-test**: composite one known frame on the GPU and compare it with the CPU result within tolerance, timing it. If anything fails, or the GPU is slower than the CPU, use the CPU path and log/show the reason in admin status (per CLAUDE.md "make failures self-explaining").
- **[prior knowledge, not retrieved]** Remote desktop (RDP) on Windows typically yields only a basic/WARP adapter or a remote-session adapter. Hybrid laptops can pick the wrong GPU. CEF and the compositor **must be on the same adapter** for shared textures ([cef osr_texture_import safety note](https://docs.rs/crate/cef/latest/source/src/osr_texture_import/mod.rs)), so choose the adapter by LUID to match CEF's, or disable the zero-copy path.
- Device loss (sleep/resume, driver update, TDR): Microsoft's guidance (search-snippet level of the Learn page) is to detect `DXGI_ERROR_DEVICE_REMOVED`/`RESET`, call `GetDeviceRemovedReason`, release everything and recreate the device and resources. Test with a forced TDR — [Handling device-lost scenarios](https://learn.microsoft.com/en-us/windows/uwp/gaming/handling-device-lost-scenarios); [GetDeviceRemovedReason](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11device-getdeviceremovedreason). **[prior knowledge, not retrieved]** In wgpu, register `device.set_device_lost_callback` and treat validation/OOM errors via `on_uncaptured_error`. On loss, the ticker switches to the CPU compositor **for the next tick** (the CPU path needs CEF `OnPaint`, so CEF's shared-texture mode would need a browser re-create, or keep both: see below) and retries the GPU path with backoff.
- Practical design: `trait Compositor { fn compose(&mut self, page: PageInput, pip: Option<PipInput>, layout) -> OutputFrame }` with `CpuCompositor` (today's code, optimised per section 1) and `GpuCompositor`. The ticker owns a `Box<dyn Compositor>` and swaps it on failure. Sinks receive either a CPU NV12/BGRA buffer or, later, a GPU texture handle with a CPU readback on demand.
- Hardware encoder fallback: probe encoders at stream start with a 1-frame test encode. If ffmpeg exits with an encoder error, retry with libx264 automatically and show "hardware encoder unavailable: <reason>" in admin status.

#### (4) Zero-copy chains
- **Windows, ideal chain:** CEF `OnAcceleratedPaint` (D3D11 shared texture, BGRA) → open on our D3D11 device (`OpenSharedResource1`) → composite on GPU (D3D11 shader or video processor with the PIP as a second stream; `VideoProcessorBlt` supports multiple input streams with alpha **[prior knowledge, not retrieved]**) → `VideoProcessorBlt` BGRA→NV12 → (a) MF H.264 encoder MFT / ffmpeg `h264_qsv/amf/nvenc` via D3D11 frames (needs in-process libav or MF, not the stdin pipe), (b) staging-texture readback of NV12 (3.1 MB) to the shm for the vcam. The vcam's own D3D path is not worth it (section 2).
- **Linux, ideal chain:** CEF DMA-BUF → Vulkan import (wgpu) → composite + NV12 compute → readback NV12/YUYV for v4l2loopback (v4l2loopback is a CPU write interface; DMA-BUF export into it is not something I found documented) and VA-API encode via DMA-BUF import (in-process libav or GStreamer).
- **Segmentation on DirectML:** **[prior knowledge, not retrieved: wgpu-hal exposing the raw `ID3D12Device`]** the D3D12 device used by wgpu's DX12 backend can be passed to ORT's DML EP (`OrtSessionOptionsAppendExecutionProviderEx_DML` takes a DML device plus a command queue — [NVIDIA end-to-end ONNX+DirectML blog](https://developer.nvidia.com/blog/end-to-end-ai-for-nvidia-based-pcs-onnx-and-directml)). Inputs must be D3D12 **buffers**, and the caller handles barriers ([DirectML barriers](https://learn.microsoft.com/en-us/windows/ai/directml/dml-barriers)). It can't share a D3D11 device directly. You'd need D3D11On12 or shared handles plus fences. Given that segmentation tensors are tiny (e.g. 256x256x3 floats ≈ 0.8 MB), a CPU round-trip is cheap. Keeping the matte on the GPU matters mainly to avoid a GPU→CPU sync point.

#### (5) Realistic costs on integrated GPUs
- A 1080p BGRA frame is 8.3 MB, NV12 3.1 MB. At 30 fps that is 249 MB/s up plus 93 MB/s down, a small fraction of iGPU/UMA memory bandwidth (tens of GB/s) and of PCIe 3.0 x16 (~16 GB/s) on discrete GPUs. **Bandwidth is not the problem. Synchronisation latency is.** wgpu readback lands at least one frame later unless the CPU blocks on `poll(Wait)` — [Bevy gpu_readback](https://dev-docs.bevyengine.org/src/gpu_readback/gpu_readback.rs.html); [re_renderer](https://docs.rs/crate/re_renderer/0.32.1/source/src/texture_readback.rs). Anecdotally, synchronous readback stalls cost "tens of ms" in WebGL and async readback saved 2–3 ms of frame time in Unity (not wgpu/1080p specific) — [Unity discussion](https://discussions.unity.com/t/asyncgpureadback-always-has-1-frame-delay/719885); [processing4#1320](https://github.com/processing/processing4/issues/1320). (Bandwidth figures are standard spec numbers and my arithmetic, not from retrieved sources.)
- On UMA iGPUs, "upload" is still a copy into a GPU-visible allocation unless using `MAP_WRITE`-able staging that the GPU reads directly. wgpu exposes `MAPPABLE_PRIMARY_BUFFERS` on some backends, but texture uploads still go through a copy. Expect about 1–3 ms of CPU+GPU time per 1080p upload/readback pair on an iGPU, plus one frame of latency if pipelined. This is my estimate; **no published measurement found**.
- Hardware MJPEG decode copy-back costs and driver quirks are reported on Intel (section 3).
- **[prior knowledge, not retrieved]** Prior art: OBS Studio composites entirely on the GPU (D3D11 on Windows, OpenGL on Linux) and keeps frames on the GPU through to hardware encoders (it is reference only, no dependency). I did not retrieve OBS architecture docs this session, so no numbers are given.

### Inferences
- **Recommended sequence:** (0) section-1 CPU fixes plus NV12 to ffmpeg; (1) hardware encoder selection with libx264 fallback; (2) measure; only if CPU is still high on target laptops, (3) wgpu compositor with CEF `accelerated_osr` input, (4) in-process encoder fed by GPU NV12. Each step has the CPU path as fallback.
- Steps (0)–(1) need no GPU API code and are fully testable on Linux with `h264_vaapi` (if the dev box has an Intel/AMD GPU) and on the user's Windows PC with `h264_qsv/amf/nvenc/mf`.

### Gaps
- No published numbers for wgpu 1080p upload/readback on Intel Iris Xe / AMD 680M, or for `VideoProcessorBlt` BGRA→NV12 throughput.
- No official confirmation that Frame Server provides a D3D manager to virtual-camera sources for Teams. VCamSample says Teams/Chrome are D3D-less.
- Guided-filter matte refinement on the GPU: no source was retrieved for costs or Rust implementations. The table entry is inference.
- No official CEF doc for the Linux `OnAcceleratedPaint` DMA-BUF payload. It is behind the cef crate feature `accelerated_osr`; behaviour under X11 vs Wayland and with the NVIDIA proprietary driver is unverified.
- No source covering `h264_mf` low-latency options. Third-party gists only for the QSV/AMF/VAAPI flags. Verify with `ffmpeg -h encoder=<name>`.
- ORT zero-copy D3D12 shared-handle import is a proposal (onnxruntime#26821), not shipped as of the retrieved page.
