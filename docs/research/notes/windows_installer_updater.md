# Windows 11 installer and automatic updates for Page2Cam

Scope: how Page2Cam (Rust, cross-built from Linux with cargo-xwin; ~300 MB zip with CEF, ffmpeg.exe, ONNX Runtime + DirectML, models, vc_redist, and a COM media-source DLL loaded by the Windows Frame Server service) should get a real installer plus automatic updates. Research date: 2026-11-18. Local context read: `scripts/package-windows.sh`, `packaging/windows/install-camera.cmd`, `packaging/windows/uninstall-camera.cmd`, `CLAUDE.md`.

What the installer must reproduce, from `packaging/windows/install-camera.cmd` (local file, not a web source): elevate; `net stop FrameServerMonitor` and `net stop FrameServer`; `regsvr32 /u` any old DLL; copy `p2c_vcam_win_source.dll` to `%ProgramFiles%\Page2Cam`; `Unblock-File`; create `%ProgramData%\Page2Cam` and grant LocalService (S-1-5-19) and Users (S-1-5-32-545) Modify; run `vc_redist.x64.exe /install /quiet /norestart`; `regsvr32` the DLL. Uninstall (`uninstall-camera.cmd`) runs `regsvr32 /u`, stops both services, and deletes the folder.

Every candidate below was tested against one constraint: **an elevated per-machine step (HKLM COM registration, stopping FrameServer, writing to Program Files) is needed at install, at any update that changes the camera DLL, and at uninstall. It should also be buildable from Linux or from a GitHub Actions Windows runner.**

## Installer technology options and trade-offs (Inno Setup, NSIS, WiX/MSI, MSIX, Velopack, Tauri/cargo-packager/cargo-dist, Squirrel, winget/Store)

### Takeaway
MSIX almost certainly can't host this app's camera DLL (an inference; no source tested it directly). The Frame Server services load it, and it has to be registered in machine-wide HKLM from a location those services can read. That leaves a classic EXE installer, either Inno Setup (built-in `regserver` and `restartreplace` file flags) or NSIS (whose installers can be built natively from Linux). The other route is Velopack, which installs the app per-user and handles delta updates, paired with a small elevated "camera component" step. WiX/MSI and Tauri's MSI output need a Windows machine, and WiX v6+ carries a maintenance fee once a project earns revenue.

### Cited Findings
**Why the DLL forces a per-machine step (primary source):**
- VCamSample, the upstream that Page2Cam's DLL is ported from: "it's not possible to register a Virtual Camera media source in HKCU, only in HKLM", because it "will be loaded by multiple processes". The COM object "must be accessible by the two Windows 11 services Frame Server & Frame Server Monitor", which "usually run as Local Service & Local System credentials respectively". Registering from a user-profile path "won't work". The fix is to copy it "somewhere where everyone has access" and register it from there. The README also says the camera "is shown in the preview window of apps such as Microsoft Teams" but "it's not rendered to the communicating party" (cause unknown). — [smourier/VCamSample README](https://github.com/smourier/VCamSample)
- The .NET port says the same (HKLM only; Frame Server and Frame Server Monitor). — [VCamNetSample (mirror)](https://github.imc.re/smourier/VCamNetSample)
- `MFCreateVirtualCamera` creates a virtual camera object that can be registered, unregistered or removed, and plugs into the Media Foundation frame server pipeline. — [mfvirtualcamera.h (Microsoft Learn)](https://learn.microsoft.com/en-au/windows/win32/api/mfvirtualcamera)

### Inferences
- **MSIX is ruled out.** Its registry virtualization (packaged COM is private; HKLM writes are blocked or redirected to HKCU) conflicts with VCamSample's primary-source rule that the media source must be in real HKLM and reachable by the LocalService/LocalSystem Frame Server processes. No source showed an MSIX-packaged MF virtual camera working. MSIX also forces a signing certificate that matches the manifest publisher. This is an inference, because no source directly tests MSIX with `MFCreateVirtualCamera`.
- **WiX/MSI** is technically fine: native COM registration, per-machine install, and Group Policy deployment. But it needs a Windows build machine (per Tauri), the OSMF terms apply to WiX v6+, and MSI authoring is the most work. For a single-developer GPL hobby project there's no reason to choose it unless enterprise or GPO deployment matters.
- **Inno Setup** covers this app's needs out of the box: `PrivilegesRequired=admin` with a Program Files install, `regserver` for the DLL, `restartreplace`/`uninsrestartdelete` for a DLL locked by Frame Server, `[Run]` entries for `vc_redist /quiet` and `net stop FrameServer`, and Pascal `[Code]` for icacls and service handling. winget recognizes Inno installers and their silent switches natively. The licence is free for a non-commercial GPL project. Its compiler (ISCC) is a Windows program, so from Linux it would run under Wine (unverified, see Gaps) or on a GitHub Actions `windows-latest` runner.
- **NSIS** is the option that verifiably builds from Linux (Tauri documents the cargo-xwin + makensis flow). It needs more hand-written script for the same jobs (DLL registration, reboot-replace, services, ACLs). Tauri's NSIS template gives `installMode: perMachine` for free. Using the Tauri bundler or cargo-packager just to emit an NSIS script is possible, but Page2Cam isn't a Tauri app, so a hand-written `.nsi` is simpler.
- **Velopack** is the only option here with built-in delta updates (next section), which matters for a 300 MB payload where CEF rarely changes. Its default per-user model doesn't conflict with the camera DLL as long as the DLL is handled separately. The app already copies the DLL to Program Files rather than registering it in place, so the app can live in `%LocalAppData%` while a small elevated step installs or updates just the DLL. Velopack's per-machine MSI path adds a WiX build that probably needs Windows (unverified), and per-machine updates would hit UAC on every update anyway.
- **Squirrel.Windows** is the predecessor of Velopack (Velopack's docs include a "migrating from Squirrel" guide: [docs.velopack.io/migrating/squirrel](https://docs.velopack.io/migrating/squirrel)). Starting a new project on Squirrel in 2026 makes no sense.

### Gaps
- No primary source confirms that Inno Setup's ISCC runs reliably under Wine on Linux, or which Inno version the GitHub Actions Windows images ship. Verify by running it.
- No source tested an MSIX-packaged MF virtual camera directly. The MSIX conclusion is an inference.
- Not fetched: cargo-dist and cargo-packager docs (cargo-dist's MSI output uses WiX, which per Tauri needs Windows; cargo-dist's built-in updater, axoupdater, wasn't checked), wixl/msitools capabilities, and NSIS's own docs for `RegDLL` and `/REBOOTOK`.
- Velopack's docs don't say whether `vpk [win] pack --msi` works from Linux (the WiX fork probably needs Windows), or whether `--veloapp-*` hooks may trigger UAC.

## Updater design (GitHub Releases check, signature/checksum verification, applying while running, locked camera DLL, elevation, rollback, deltas, Rust crates)

### Takeaway
Use one of two approaches. (A) Velopack's Rust crate gives GitHub-Releases-backed updates with Zstandard per-file deltas, staged apply-on-restart and no UAC for the per-user app. Add a separately versioned, elevated "camera component" step that runs only when the DLL changes. (B) A small custom updater (`self_update`-style: GitHub Releases plus ed25519/zipsign verification) downloads a signed Inno/NSIS installer and runs it silently and elevated. B is simpler, but users re-download ~300 MB and see a UAC prompt on every update. Either way the DLL replacement must stop FrameServer and FrameServerMonitor, with replace-on-reboot as the fallback.

### Cited Findings
- Velopack deltas are generated automatically when a previous release is in the output dir (or pulled in CI via `vpk download`). "Delta packages use Zstandard to create binary patches of individual files in your package." Modes are `None`, `BestSpeed` (default) and `BestSize` (~bsdiff-level size, much slower). Clients apply each intermediate delta in order onto the local package in `%LocalAppData%\{packId}\packages`. A heuristic chooses between N deltas and the latest full package based on full size, combined delta size and delta count. No single file may exceed 2 GB. `UpdateManager` searches GitHub Releases for deltas, and each release should contain one full package plus one delta. — [Velopack docs: delta updates](https://docs.velopack.io/packaging/deltas)
- `self_update` 1.3.3: backends for GitHub Releases (default), GitLab, Gitea, Gitee, S3-compatible and a generic `manifest.json`. The `signatures` feature verifies zipsign-signed `.zip`/`.tar.gz` artifacts with an "ed25519ph verifying key". It replaces the running exe via the `self-replace` crate; on Windows "the new binary is spawned and the current process exits". For directory bundles, "the swap fails, and rolls back, if the process holds files inside the bundle open". — [self_update docs.rs](https://docs.rs/self_update/latest/self_update/)
- Inno `restartreplace` covers files locked by another process by scheduling the replacement for the next reboot. — [Inno Setup [Files] help](https://jrsoftware.org/ishelp/topic_filessection.htm)
- The DLL is loaded by the Frame Server and Frame Server Monitor services. — [VCamSample README](https://github.com/smourier/VCamSample)
- Updating per-machine installs normally needs admin/UAC. — [codenote.net](https://codenote.net/en/posts/windows-desktop-app-per-machine-silent-auto-update-patterns/). Advanced Installer sells an updater *service* that avoids elevation for per-machine-only projects. — [Advanced Installer: elevated updates](https://www.advancedinstaller.com/user-guide/qa-elevated-updates.html)

### Inferences
- Because the services load the DLL, they hold it locked while running, so it can't be overwritten in place without stopping them or scheduling a replace on reboot.
- Advanced Installer's product suggests that updating Program Files content without UAC requires an always-running privileged service, which is more than Page2Cam needs.

**Approach A, the Velopack hybrid. This is the Phase 2 design in the final recommendation; Phase 1 is approach B below:**
1. **Packaging (Linux, existing pipeline):** after `package-windows.sh` assembles `dist/Page2Cam-windows-x64/`, run `vpk [win] pack --packId Page2Cam --packVersion X.Y.Z --packDir dist/Page2Cam-windows-x64 --mainExe page2cam.exe`, with `vpk download github` first so a delta against the last release is generated. Upload with `vpk upload github` (or `gh release upload`). CEF, ffmpeg, onnxruntime and the models change rarely, so the per-file Zstd deltas should be a few MB for code-only releases instead of 300 MB (inferred from the per-file delta design; actual size unmeasured).
2. **In the app:** call `VelopackApp::build().run()` first in `main`, before CEF's `maybe_run_subprocess()` (both inspect argv; check that the ordering works with CEF helper processes). From the admin page, offer "Check for updates" using `UpdateManager` with a GitHub source, download in the background, and apply on restart (Velopack swaps the `current` dir while the app isn't running, which avoids locked CEF files).
3. **Camera component, versioned separately:** embed a `CAMERA_COMPONENT_VERSION` (bump only when the DLL or shm protocol changes). On startup, read the installed DLL's version from `%ProgramFiles%\Page2Cam\p2c_vcam_win_source.dll` (file version resource, or a registry value written at install). If it's missing or older, the admin UI shows "Install/update camera (needs admin)", which relaunches `page2cam.exe --install-camera` via `ShellExecuteW(..., "runas", ...)`. That subcommand reimplements `install-camera.cmd` in Rust: stop FrameServerMonitor/FrameServer via the Service Control Manager, `DllUnregisterServer` the old copy, copy the new file in (if it's locked, use `MoveFileExW(MOVEFILE_DELAY_UNTIL_REBOOT)` and say a reboot is needed), set ACLs on `%ProgramData%\Page2Cam`, run vc_redist silently if the VC runtime is absent, `DllRegisterServer`, and restart the services. That gives one UAC prompt at first install, then only when the DLL changes. Keep the shm protocol backward compatible, or have the app refuse an old DLL with a clear status message, so a skipped camera update fails visibly (this fits CLAUDE.md's "self-explaining failures" rule).
4. **Uninstall:** in the `--veloapp-uninstall` hook (30 s limit), spawn the elevated `--uninstall-camera` helper (unregister, stop services, delete files) and exit. Because it may not be safe to depend on UAC inside the hook, also ship an "Remove camera" button and keep `uninstall-camera.cmd` as a manual fallback.
5. **Verification:** Velopack verifies package hashes from its release feed (a general property of the feed, not confirmed in a source fetched here). Authenticode-sign `page2cam.exe`, `Setup.exe`, `Update.exe` and the DLL so that Smart App Control doesn't block them (next section).
6. **Rollback:** Velopack keeps the previous full package locally. A failed update leaves `current` untouched (inferred; not verified in fetched docs). For the camera DLL, keep the previous DLL as `.bak` until the new one registers.

**Approach B (simpler, no Velopack):** an Inno or NSIS per-machine installer plus a Rust check of `GET https://api.github.com/repos/prasadvittaldev/Page2Cam/releases/latest`. Compare semver, download `Page2Cam-Setup-X.Y.Z.exe` plus a `.minisig`/zipsign signature, verify against an ed25519 public key compiled into the binary (and check the Authenticode signature with `WinVerifyTrust` once signing exists), then launch `Setup.exe /VERYSILENT /SUPPRESSMSGBOXES` elevated and exit. The installer stops the services, replaces files (`restartreplace` for the DLL), re-registers, and relaunches the app. Downsides: a full ~300 MB download each time, a UAC prompt on every update, and no deltas unless the installer is split (for example, CEF/models as a separately versioned component download), which reinvents Velopack.

**Why not `self_update` alone:** it is built to replace a single executable. For directory bundles the swap fails if files are open, and it has no deltas and no install/uninstall registration. It's fine as the GitHub-check and signature-verify layer in approach B.

### Gaps
- No source confirmed how the Velopack Rust API (`VelopackApp`, `UpdateManager`, GitHub source) coexists with CEF's subprocess relaunch, or whether Velopack verifies a signature (as opposed to a hash) of release feeds.
- No source fetched documented whether `net stop FrameServer` reliably releases the DLL, or whether Frame Server restarts on demand while files are being copied. The current `install-camera.cmd` behaviour is the only evidence, and it has never run on real hardware per CLAUDE.md.
- The minisign crate API wasn't fetched. zipsign (via `self_update`) is the sourced ed25519 option.

## Per-machine vs per-user install, settings/log locations, uninstall cleanup

### Takeaway
The app should not live in Program Files with settings next to the exe. Install the app per-user (Velopack) or per-machine (Inno/NSIS), but move writable state out of the install dir in both cases: settings to `%AppData%\Page2Cam\config.toml` (which the code's `<config_dir>/page2cam/config.toml` fallback already gives), logs to `%LocalAppData%\Page2Cam\logs`, and keep the DLL log in `%ProgramData%\Page2Cam`. Only the camera DLL has to be machine-wide.

### Cited Findings
- Velopack's per-user install lives in `%LocalAppData%\{packId}` and stores packages in `%LocalAppData%\{packId}\packages`. — [Velopack installer docs](https://docs.velopack.io/packaging/installer); [Velopack deltas](https://docs.velopack.io/packaging/deltas)
- The virtual-camera DLL must be registered in HKLM, from a folder the LocalService/LocalSystem Frame Server services can read. — [VCamSample README](https://github.com/smourier/VCamSample)
- Tauri's default NSIS mode is per-user in `%LOCALAPPDATA%` without admin; per-machine needs admin. — [Tauri Windows installer](https://tauri.app/distribute/windows-installer/)
- SignPath's terms require signed installers to "include instructions or automated facilities for uninstallation" and not to change system configuration without proper warnings. — [SignPath Foundation terms](https://signpath.org/terms)

### Inferences
- Local facts from the repo (not web sources): per CLAUDE.md, settings resolve as `--config`, then `page2cam.toml` next to the exe, then `<config_dir>/page2cam/config.toml`, and logs go next to the exe on Windows. `package-windows.sh` copies `packaging/windows/page2cam.toml` into the package. The installer build should stop shipping `page2cam.toml` next to the exe (or the code should prefer the config_dir file when the exe sits under Program Files or a Velopack `current` dir), because Program Files isn't user-writable and Velopack replaces the app folder on every update. On first run, migrate an existing `page2cam.toml` from the old zip location. Logs should move to `dirs::data_local_dir()/Page2Cam/logs`, and the admin page should link to them.
- Uninstall must, while elevated: unregister the DLL (`regsvr32 /u` or `DllUnregisterServer`), stop FrameServerMonitor/FrameServer if the DLL is locked (or queue its deletion for reboot), delete `%ProgramFiles%\Page2Cam`, and remove `%ProgramData%\Page2Cam` (the DLL log). Optionally offer to remove `%AppData%\Page2Cam` (settings) and the keyring entry holding the stream key. Leave vc_redist installed, since it's shared. Any virtual camera started with `MFCreateVirtualCamera` and session lifetime disappears when the app stops; if a system-lifetime camera is ever used, uninstall must also call `IMFVirtualCamera::Remove()` (an inference from the API description of register/unregister/remove: [mfvirtualcamera.h](https://learn.microsoft.com/en-au/windows/win32/api/mfvirtualcamera)).
- Per-machine (Inno/NSIS) is the more conventional choice for software that installs a system camera, and it gives one Add/Remove Programs entry that cleans everything. Per-user with a separate camera step gives UAC-free, delta-sized updates, but two artefacts (app and camera component) have to be kept in sync.

### Gaps
- The `MFCreateVirtualCamera` lifetime choice (session vs system) used by `windows_cam.rs` wasn't re-checked against the code for this note.

## Code signing in 2025-2026 (SmartScreen, Artifact Signing, EV vs OV, signing from Linux, SignPath)

### Takeaway
Signing is no longer optional polish. On Windows 11, Smart App Control blocks unsigned executables that lack reputation, and EV no longer buys instant SmartScreen trust. The cheapest real paths are Azure Artifact Signing (from $9.99/month, but individuals must be in the US or Canada) or the free SignPath Foundation programme for OSS (certificate in SignPath Foundation's name, builds must come from CI). Both can be driven from Linux with jsign 7.x.

### Cited Findings
- "EV certificates no longer bypass SmartScreen… Paying a premium for EV solely to avoid SmartScreen warnings is no longer justified." OV and EV signed apps both show "unrecognized" until reputation builds. Unsigned files start at zero reputation with every new version, and reputation transfers only between versions signed by the same publisher identity. Clearing the warning "can take several weeks and hundreds of clean installs". "On Windows 11 devices, the Smart App Control feature may supersede SmartScreen Application Reputation. Smart App Control will block execution of unsigned files unless the file has a positive reputation… [it applies] to all executable files, not just those downloaded from the Internet." Artifact Signing "Starts at $9.99/month". Store-distributed apps never get SmartScreen download warnings. — [Microsoft Learn: SmartScreen reputation (2026-05-04, updated 2026-08)](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)
- Artifact Signing eligibility (quickstart updated 2026-11-17): "Public Trust certificates are available to organizations in the United States, Canada, the European Union, the United Kingdom, Australia, New Zealand, Japan, South Korea, Singapore, Switzerland, Norway, and Israel. Individual developers must be located in the United States or Canada." Individual validation uses an Azure billing account of type Individual and AU10TIX/Verified ID checks with a government ID. — [Artifact Signing quickstart](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart)
- This supersedes a May 2025 Q&A thread that said only US/Canada organizations with 3+ years of history could onboard. — [Microsoft Q&A (May 2025, outdated)](https://learn.microsoft.com/answers/a/2028104)
- FAQ: free, trial and sponsored Azure subscriptions are not supported; a paid subscription is required. Billing isn't pro-rated. Custom CN/O isn't allowed. Artifact Signing doesn't issue EV and has "no plan to issue EV certificates in the future". SmartScreen prompts stop "once the file hash has sufficient download history". — [Artifact Signing FAQ (2026-11-17)](https://learn.microsoft.com/en-us/azure/artifact-signing/faq)
- Pricing tiers: Basic includes 5,000 signatures/month and 1 certificate profile of each type; Premium includes 100,000 signatures/month and 10 profiles. Dollar amounts didn't render on the page. — [Artifact Signing pricing](https://azure.microsoft.com/en-us/pricing/details/artifact-signing/)
- SignPath Foundation (free for OSS): needs an OSI licence with no commercial dual-licensing; "The project may not contain any proprietary, non open-source component". GPLv3 "System Libraries" are allowed, and "You may include unsigned binaries of upstream OSS projects, e.g. DLL files". Signed binaries must be automated builds from the repository, and each release is manually approved. The team that signs must be the team that develops; MFA is required. Download pages need a "Code signing policy" section and a privacy policy. "The code signing certificate is issued to SignPath Foundation." Required attribution: "Free code signing provided by SignPath.io, certificate by SignPath Foundation". Installers must include uninstall facilities. The code of conduct "is still in a draft version". — [SignPath Foundation terms](https://signpath.org/terms); [signpath.org](https://signpath.org/)
- jsign 7.6 (2026-10-12) is a "Platform independent command line tool (Linux, macOS and Windows)". It supports Azure Artifact/Trusted Signing (added in 7.0), Azure Key Vault and SignPath (added in 7.1), and signs EXE, DLL, MSI, CAB/CAT, APPX/MSIX, NuGet `.nupkg` and scripts. It is "particularly well-suited for signing executable wrappers and installers generated by tools such as NSIS". — [jsign GitHub](https://github.com/ebourg/jsign)

### Inferences
- Choice depends on where the developer lives (unknown here): **US/Canada individual → Artifact Signing** (the cert shows the developer's own name; ~$9.99/month; sign from Linux with `jsign --storetype TRUSTEDSIGNING`). **Elsewhere → SignPath Foundation**, if the bundle passes review (publisher shown as "SignPath Foundation"; release builds must move to GitHub Actions so SignPath can verify origin), or a commercial OV certificate in a cloud HSM.
- Open question for SignPath: whether bundled `vc_redist.x64.exe` (Microsoft proprietary), `DirectML.dll` (Microsoft redistributable) and CEF's `libcef.dll` count as acceptable "System Libraries" or upstream OSS. vc_redist and DirectML are not open source. One option that may comply is to download vc_redist at install time instead of bundling it. Ask SignPath before applying; this is not decided here.
- Shipping unsigned now carries a concrete cost: with Smart App Control on, Windows 11 may block `page2cam.exe`, ffmpeg.exe and the installer outright, not just warn. Third-party binaries (ffmpeg.exe, onnxruntime.dll, CEF) arrive with their own signatures or none, and signing your own `page2cam.exe`, DLL and installer doesn't cover them.
- Keep one consistent signing identity across releases, so that reputation transfers between versions (per Microsoft).

### Gaps
- Exact Basic/Premium USD prices: only "starts at $9.99/month" is sourced.
- SignPath approval time and OV/EV type of its certificate: not stated on the fetched pages.
- Whether osslsigncode can drive Artifact Signing: not fetched; jsign is the sourced Linux option.
- Whether Velopack's `vpk` can sign through jsign or a sign template on Linux: not fetched.

## winget (and Microsoft Store) as an additional channel

### Takeaway
After the installer exists, winget is cheap to add. It supports Inno, Nullsoft, EXE, MSI/WiX and MSIX installer types; Inno/NSIS silent switches are automatic. A manifest is a YAML PR to microsoft/winget-pkgs (via `wingetcreate`), and the only hard requirement found is that the installer supports silent install. The Store would remove SmartScreen warnings but implies MSIX or Store-specific packaging, which the camera DLL makes impractical (inference).

### Cited Findings
- Required manifest fields: PackageIdentifier, PackageVersion, PackageLocale, Publisher, PackageName, License, ShortDescription, Installers (Architecture, InstallerType, InstallerUrl, InstallerSha256), ManifestType, ManifestVersion (1.12.0). Installer types: "exe, msi, msix, inno, wix, nullsoft, appx, font". For Nullsoft or Inno installers, "the client will automatically set the silent and silent with progress install behaviors". "All tools must support a silent install." Package identifiers are unique, with one PR per version. PackageName and Publisher should match the Add/Remove Programs entry for `upgrade`. MSI installers should include the product code. Tooling: `wingetcreate new` (can submit the PR automatically) or YAMLCreate.ps1. — [Microsoft Learn: Create your package manifest (2026-09-14)](https://learn.microsoft.com/en-us/windows/package-manager/package/manifest)
- Store apps are signed by Microsoft and "never subject to SmartScreen download warnings". — [Microsoft Learn: SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)

### Inferences
- With an Inno or NSIS per-machine installer: create `Page2Cam.Page2Cam` (or `PrasadVittal.Page2Cam`) with InstallerType `inno`/`nullsoft`, Scope `machine` and the GitHub release URL. Automate updates from a release workflow (for example with `wingetcreate update --submit`, or the community tool komac). `winget upgrade` then becomes a second update channel. The in-app updater should notice a winget-managed install and avoid fighting it, or simply still work, because both run the same installer.
- With Velopack, `Setup.exe` would be submitted as type `exe` with the Velopack silent switch. winget is then mostly a discovery channel, since Velopack updates the app itself.
- winget downloads still carry Mark-of-the-Web/SmartScreen considerations, and Smart App Control still applies, so signing comes first.

### Gaps
- Whether winget-pkgs validation pipelines reject unsigned installers, or ones flagged by Defender/SmartScreen, wasn't confirmed from primary docs. winget's `ElevationRequirement` and `Scope` field semantics weren't fetched (schema link: [installer.md 1.12.0](https://github.com/microsoft/winget-pkgs/blob/master/doc/manifest/schema/1.12.0/installer.md)).
- Microsoft Store acceptance of a Win32 EXE/MSI that registers an HKLM COM camera wasn't researched.

## Recommendation and implementation outline

### Takeaway
**Phase 1 (ship soon, lowest risk):** a per-machine **Inno Setup** installer (or NSIS, if everything must build on Linux). It reproduces `install-camera.cmd` with `regserver` + `restartreplace`, includes vc_redist and uninstall, and adds a lightweight Rust update checker that downloads and verifies the signed installer from GitHub Releases. **Phase 2 (if 300 MB updates or UAC-per-update annoy users):** move the app payload to **Velopack** (per-user, Zstd deltas, built with `vpk [win] pack` on Linux) and keep the camera DLL as a separately versioned, elevated component installed by `page2cam.exe --install-camera`. **In parallel:** get signing (Artifact Signing if US/Canada, otherwise SignPath) and add winget.

### Cited Findings
- Inno flags `regserver`, `restartreplace` and `uninsrestartdelete` exist for exactly the DLL register / locked-file / uninstall cases. — [Inno Setup [Files] help](https://jrsoftware.org/ishelp/topic_filessection.htm)
- NSIS installers can be cross-built from Linux with cargo-xwin; MSI can't. — [Tauri Windows installer](https://tauri.app/distribute/windows-installer/)
- Velopack: Windows packages can be built on any OS, with per-file Zstd deltas and GitHub Releases support. — [Velopack cross compiling](https://docs.velopack.io/packaging/cross-compiling); [Velopack deltas](https://docs.velopack.io/packaging/deltas)
- jsign signs EXE/DLL/MSI from Linux via Artifact Signing or SignPath. — [jsign](https://github.com/ebourg/jsign)
- Smart App Control blocks unsigned executables without reputation. — [Microsoft Learn: SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)

### Inferences
**Caveat:** the following names were written from memory, not from fetched docs, and must be checked against the official documentation before use. Inno: `CloseApplications`, `AppMutex`, `[Dirs] Permissions: localservice-modify`, `SetupLogging`, `/SUPPRESSMSGBOXES`, `x64os`, and the assumption that `regserver` files are unregistered automatically at uninstall. NSIS: `RegDLL`, `Rename /REBOOTOK`. Velopack: `VelopackApp::build().run()`, `UpdateManager`, `vpk download/upload github`, and the `current` dir. jsign: `--storetype TRUSTEDSIGNING`. wingetcreate: `update --submit`.

Implementation outline for Phase 1 (Inno):
1. `packaging/windows/page2cam.iss`: `AppId={{fixed GUID}}`, `PrivilegesRequired=admin`, `ArchitecturesAllowed=x64os`, `ArchitecturesInstallIn64BitMode=x64os`, `MinVersion=10.0.22000` (Windows 11), `DefaultDirName={autopf}\Page2Cam`, `CloseApplications=yes`, `AppMutex=Page2CamRunning` (the app creates this mutex), `UninstallDisplayIcon`, `LicenseFile=LICENSE.txt`.
2. `[Files]`: the whole `dist/Page2Cam-windows-x64` tree with `ignoreversion`, except the DLL, which gets `Flags: ignoreversion regserver restartreplace uninsrestartdelete 64bit`. Drop `install-camera.cmd`, `uninstall-camera.cmd` and `page2cam.toml` from the installed set. `vc_redist.x64.exe` goes into `{tmp}` with `deleteafterinstall`.
3. `[Code]` `PrepareToInstall`: stop FrameServerMonitor and FrameServer (`sc stop`, or `Exec('net', 'stop FrameServer /y', ...)`), so `regserver` and the copy normally succeed without a reboot. `CurStepChanged(ssPostInstall)`: create `{commonappdata}\Page2Cam` with `[Dirs] Permissions: localservice-modify users-modify`. `[Run]`: `vc_redist.x64.exe /install /quiet /norestart` (skip if `HKLM\SOFTWARE\Microsoft\VisualStudio\14.0\VC\Runtimes\x64\Installed` = 1), then optionally launch page2cam.exe `nowait postinstall skipifsilent`. `[UninstallRun]` / `CurUninstallStepChanged`: stop the services before files are removed (`regserver` files are unregistered automatically at uninstall), then delete `{commonappdata}\Page2Cam`, and optionally offer to delete `{userappdata}\Page2Cam`.
4. App changes: settings default to `%AppData%\Page2Cam\config.toml` when running from an installed location (the existing config_dir fallback), logs go to `%LocalAppData%\Page2Cam\logs`, migrate an old `page2cam.toml`, create the `AppMutex`, and make `windows_cam.rs` report "camera component missing/outdated, reinstall or repair" with the installed DLL version.
5. Build: on a GitHub Actions `windows-latest` job (needed anyway if signing goes through SignPath), restore the Linux-built `dist/` artefact and run `ISCC.exe /DVersion=X.Y.Z page2cam.iss`. Or run ISCC under Wine on the Linux box (unverified). For a Linux-only path, use NSIS `makensis` with an equivalent `.nsi` (`RegDLL`, `Rename /REBOOTOK`, `RequestExecutionLevel admin`, `SetShellVarContext all`).
6. Sign: `page2cam.exe`, `p2c_vcam_win_source.dll`, then the installer `Page2Cam-Setup-X.Y.Z.exe`, using jsign (Artifact Signing or SignPath), timestamped.
7. Updater (Rust, new small module or crate, for example `p2c-update`): on startup, at most once a day, and only if enabled in settings, `GET /repos/prasadvittaldev/Page2Cam/releases/latest` (ETag-cached, User-Agent set), compare semver with `CARGO_PKG_VERSION`, and show "Update X.Y.Z available" in the admin UI. On click: download the setup exe to `%TEMP%`, verify its SHA-256 against a signed `SHA256SUMS` (minisign/zipsign ed25519 key baked into the binary) and, once signing exists, `WinVerifyTrust` plus the expected publisher subject. Then `ShellExecuteW("runas", setup, "/VERYSILENT /SUPPRESSMSGBOXES /NORESTART")` and exit cleanly (stopping the stream and vcam first). If the installer reports a pending reboot (`restartreplace`), the admin page says so on next start. Rollback: Inno replaces in place, so rollback means re-running the previous installer, which is acceptable for Phase 1. **Open design point, relaunch after a silent update:** a `[Run]` entry marked `skipifsilent` never runs under `/VERYSILENT`, and anything the elevated installer starts would itself run elevated, which is wrong for this app. Options: before exiting, the app spawns a non-elevated waiter process that relaunches `page2cam.exe` when the installer exits; or the installer uses an unelevated-launch technique (for example Inno's `runasoriginaluser` [Run] flag, which is unverified here).
8. winget: `wingetcreate new` once with InstallerType `inno`, Scope `machine`; then `wingetcreate update --submit` from the release workflow.

Phase 2 (Velopack hybrid), when needed: `vpk [win] pack` the same `dist/` dir with deltas, add `velopack` crate hooks in `main` (before `maybe_run_subprocess`), move the camera install/repair into `page2cam.exe --install-camera` (elevated via `runas`, versioned by `CAMERA_COMPONENT_VERSION`), and do uninstall cleanup through `--veloapp-uninstall` plus a manual "Remove camera" fallback. Expected benefit: code-only updates are delta-sized, with no UAC prompt unless the DLL changed.

### Gaps
- None of these flows has been run on real Windows 11 hardware. The DLL itself has never run (CLAUDE.md "Known open risks"), so the installer's camera step must log loudly (Inno `SetupLogging=yes`; the app's admin status) and be checked on the user's PC.
- Real Velopack delta sizes for this CEF bundle are unmeasured; a test pack of two consecutive builds would settle it.
